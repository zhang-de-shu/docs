# 第一部分 概念框架：记忆到底是什么

## 1.1 一张图看清全貌

记忆不是单一功能，而是一个分层系统。2025→2026 业界已收敛到一个源自认知科学的分类，几乎所有主流框架（Mem0/Letta/Zep/Cognee）都用它：

```
┌─────────────────────────────────────────────────────────┐
│                     Agent 记忆系统                       │
│                                                         │
│  工作记忆 Working ── 当前上下文窗口，看「新鲜度」            │
│  ─────────────────────────────────────────────────────  │
│  长期记忆 Long-term：                                    │
│    情景记忆 Episodic ── 「发生过什么」原始轨迹（原料）        │
│         │  蒸馏/固化 distillation/consolidation          │
│         ▼                                               │
│    语义记忆 Semantic ── 「X 是什么」事实/偏好（知识一半）     │
│    程序性记忆 Procedural ── 「怎么做」技能/规则（知识另半）   │
└─────────────────────────────────────────────────────────┘
        └──────── 「知识库」= 语义 + 程序性这两层 ────────┘
```

## 1.2 记忆 vs 知识：不是同一个概念，是同一套架构的不同层

**二者是"原料"与"成品"的关系。**

| 层 | 回答的问题 | 内容 | 类比 | 是不是"知识库" | 检索按 |
|----|-----------|------|------|--------------|--------|
| **工作记忆 Working** | "现在在处理什么" | 当前上下文窗口 | 短时记忆 | ❌ | 新鲜度 |
| **情景记忆 Episodic** | "发生过什么" | 原始对话、完整任务轨迹 | 流水账日记 | ❌ 原料 | 时间邻近性 |
| **语义记忆 Semantic** | "X 是什么" | 事实、定义、实体关系、用户偏好 | 知道的事实 | ✅ **知识库的一半** | 语义相关性 |
| **程序性记忆 Procedural** | "该怎么做" | 规则、技能、成功工具调用序列、踩坑教训 | 学会的技能 | ✅ **知识库的另一半** | 语义相关性 |

**关键区分（企业级 Agent 最常见的架构错误就是把这几层搞混）：**

- **知识库 ⊂ 语义记忆**：狭义"知识库/事实库"只是语义记忆里的可查询子集（定义、实体属性）。
- **记忆 ⊃ 知识库**：记忆是更大的系统，涵盖工作 + 情景 + 语义 + 程序性四层。
- "**基于使用记录构建的知识库**" = 从**情景记忆**（原始使用轨迹）中，通过**蒸馏 / 固化**，产出**语义记忆 + 程序性记忆**。
- **三层检索语义完全不同**，用同一套检索策略是常见错误：记忆看时间邻近性、知识看语义相关性、工作记忆看新鲜度。

> **一句话：知识 ≠ 记忆全集，知识 = 记忆里被提炼过的那部分。**

# 第二部分 记忆分层详解

## 2.1 工作记忆（Working Memory）

- 就是当前 LLM 上下文窗口里能直接看到的内容。
- 瓶颈：窗口有限，且计算/显存随长度**二次方增长**，长上下文**边际收益递减**（"lost in the middle"）。
- 这正是"虚拟上下文管理"（见 Letta.md）要解决的核心问题——用分页制造"无限上下文"的错觉。

## 2.2 情景记忆（Episodic）——知识的唯一原料

- 内容：完整的对话记录、任务执行轨迹（trajectory），含中间推理、工具选择、恢复尝试、失败模式。
- **价值**：揭示"发生过什么"，是拓宽 Agent 能力的关键原料。
- **陷阱**：原始轨迹**冗余且有噪声**——成功 trace 里混着大量无关步骤，失败 trace 里也可能藏有用的局部决策。
- **所以不能直接当知识用**：直接把 session 流水账当知识 → 检索到噪声、冗余、自相矛盾的上下文（最常见错误）。必须经蒸馏。

## 2.3 语义记忆（Semantic）——事实层知识库

- 内容：事实、定义、实体关系、用户偏好（"用户偏好公制单位"、"HQ 在阿姆斯特丹"）。
- 写入路径：**后台抽取步骤**（extraction）——把情景蒸馏成事实。**可以自动写**。
- 治理需求：**认证 + 新鲜度**（certification & freshness）。
- 存储：向量库、知识图谱、治理型数据目录。
- 成熟度：**高**。主流框架都做得不错（Mem0 是这层的代表）。

## 2.4 程序性记忆（Procedural）——技能层知识库

- 内容：规则、技能、学到的工作流、成功的工具调用序列、行为启发式。
- 回答"怎么做"，而非"是什么"。
- 两种存在形式（CoALA 框架）：① 隐式在 LLM 权重里（**运行时不可改**）；② 显式在 Agent 代码/prompt/playbook/可加载 skill 里（**这才是设计面**）。
- 写入路径：**必须经审慎的 promotion + 校验**——这是唯一一条**永远不该全自动**的写入路径。
- 治理需求：**版本管理 + 回滚**（versioning & rollback）。
- 成熟度：**最低、最不成熟，但最有价值**。是本篇第四部分的主题。

> **ROI 对比**：一条事实检索得当，省一次查询；一条**校验过的程序（playbook）**检索得当，省掉**整条试错轨迹**——每次走错路、每次失败工具调用、每个烧掉的 token。团队实测：第二次带 playbook 做同一任务，trace 更短、更便宜、更可靠。

## 2.5 小结：四层记忆各自的定位

至此四层讲完，一句话锁定各自角色，作为后续章节的地基：

| 层 | 一句话 | 写入是否可自动 | 后文对应 |
|----|--------|--------------|---------|
| 工作记忆 | 窗口里能直接看到的 | —（靠分页/摘要管理） | 第三部分虚拟上下文 |
| 情景记忆 | 知识的唯一原料，必须蒸馏 | 自动留存 | 第四部分蒸馏输入 |
| 语义记忆 | 事实层知识库 | ✅ 可后台自动抽取 | 第三部分 |
| 程序性记忆 | 技能层知识库，最有价值最不成熟 | ❌ 必须校验后 promote | 第五部分 skill 生成 |

> 到这里只讲了"记忆分几层"。**每一层具体用什么数据结构存**（向量？图？markdown？）是下一部分——第三部分把认知分层落到工程存储。

# 第三部分 每层记忆怎么存：表示形式与存储选型

> 上一部分是**认知维度**（记忆分几层）；这一部分是**工程维度**（每层落到磁盘上长什么样）。两者不冲突——是"分类"和"实现"的关系。核心问题：一个事实/一条技能，到底该存成向量、图、JSON 还是 markdown？

## 3.1 一个常见误解：知识不止 skill 一种形式

很多人以为"从记录学知识 = 生成 skill"。其实 skill（代码）只是**程序性知识**的一种载体。按知识类型看，落地形式远比 skill 丰富——第四、五部分聚焦的 skill 生成，只是下表 ⑤ 这一格的极致做法：

| 知识类型（对应 2.3/2.4） | 回答 | 典型表示形式 | 例子 |
|---------|------|------------|------|
| **语义知识**（是什么）→ 语义记忆 | "X 是什么" | ① 自然语言事实 ② 知识图谱三元组 ③ 结构化 JSON profile ④ 规则/约束 | "用户偏好公制"；`(用户)-[偏好]->(咖啡店A)`；`{tone:"简洁"}`；"DELETE 该表需双人审批" |
| **程序性知识**（怎么做）→ 程序性记忆 | "该怎么做" | ⑤ **skill / 代码** ⑥ playbook / SOP ⑦ few-shot 范例 ⑧ 工作流模板 | Voyager 可执行函数；退款处理手册；成功案例注入 prompt |
| **关联知识**（什么相关）→ 跨层 | "谁和谁有关" | ⑨ 知识图谱的边 + 出处 provenance | 症状→诊断；产品→类目；claim 来自哪条消息 |

## 3.2 六种主流存储形式（各层都可能用到）

| 形式 | 擅长 | 短板 | 主要承载哪层记忆 | 代表 |
|------|------|------|----------------|------|
| **① 向量 embedding** | 模糊语义召回、快速事实查找 | 表达不了显式关系/层级 | 情景、语义 | Mem0、pgvector/Qdrant |
| **② 知识图谱（实体-关系-属性）** | 多跳推理、全局理解、出处追溯 | 构建/维护成本高 | 语义、关联 | Graphiti、Cognee |
| **③ 结构化 JSON / KV / 规则** | 原子化精确查找、硬约束 | 不擅长模糊语义 | 语义（profile/权限） | 用户 profile、权限规则 |
| **④ 自然语言事实 / 摘要** | 压缩情景历史，密度高、好检索 | 需抽取管线 | 情景→语义的中间态 | Mem0 抽取、摘要固化 |
| **⑤ Markdown 文件** | 透明可读可 grep，coding agent 最普及 | 无结构化检索 | 程序性、语义 | CLAUDE.md、OpenViking、ReMe |
| **⑥ 代码 / 配置 / few-shot** | 程序性知识的直接载体 | 写入危险，需校验（见 2.4） | 程序性 | Voyager skill、Agent Skills |

> `(用户)-[偏好]->(咖啡店A, 上周二下单, 聊晨间习惯时提到)` —— 图能记住关系与上下文，向量只能捞出"用户喜欢咖啡"这条相似片段。**vector 答"什么相似"，graph 答"什么逻辑相关"。**

## 3.3 选型三条铁律

1. **按记忆层分存分检，别用一套存储装全部**（最常见失败）：情景/语义/程序性全塞一个向量库、同一套检索逻辑 → 噪声互相污染。正解——语义/情景用向量库、关系用图库、程序性用 config/task-type 触发（不是最近邻）。检索语义本就不同（见 1.2）。
2. **2026 共识是"混合"，不是二选一**：向量做语义召回 + 图做多跳推理与出处 + 结构化做精确事实。主流生产栈（Mem0/Graphiti/Cognee）都是向量 + 图混合。图是表达力最强的通用结构（线性 buffer、向量集都可看成图的特例），但成本最高，按需用。
3. **所有形式的共同敌人是新鲜度（staleness）**：任何事实被高频检索时一直"自信"，直到现实变了就"自信地错"。这正是 Graphiti/Zep 用**时序知识图谱**（双时态 valid_at/invalid_at）的原因——不删旧事实，只标失效时间。

# 第四部分 从使用记录到知识（蒸馏/固化）

## 4.1 范式转移：知识中心的自我改进

> **knowledge-centric self-improvement**：不再优化 Agent 本身（prompt/workflow/权重），而是让 Agent 保持通用、可抛弃，把"改进"沉淀到一个**外部、可审查、可迁移的知识库对象**里。好处：改进可检查、可移植、不绑定特定 Agent 设计。

## 4.2 为什么原始记录必须蒸馏

- 冗余噪声（见 2.2）。
- 直接堆原始轨迹 = token 爆炸 + 检索噪声。
- 蒸馏成结构化技能后，SkillRL 实测相比存原始轨迹**压缩 10–20% token**，同时提升推理效用。

## 4.3 三阶段生命周期（skill-augmented agent 通用工作流）

```
使用记录(trajectory)
     │
     ▼
┌─────────────────────────────────────────────┐
│  ① Skill Distillation  蒸馏                 │
│     成功轨迹 → 策略性模式(strategic patterns) │
│     失败轨迹 → 简洁教训(lessons from failure) │
├─────────────────────────────────────────────┤
│  ② Skill Selection     选择                 │
│     当前任务从库里挑相关技能                    │
├─────────────────────────────────────────────┤
│  ③ Skill Utilization   使用                 │
│     在选中技能指导下执行 → 产生新轨迹 → 回到①    │
└─────────────────────────────────────────────┘
```

## 4.4 知识库的分层组织（Hierarchical SkillBank）

- **通用技能 General Skills**：跨任务的普适策略指导。
- **任务特定技能 Task-Specific Skills**：某类任务的启发式规则。

## 4.5 三种可学习的构建能力（SkillComposer 拆法）

| 能力 | 作用 | 对应记忆操作 |
|------|------|------------|
| **Skill Create** | 从原始轨迹抽取可复用程序性知识 | consolidation |
| **Skill Merge** | 合并语义相似技能 → 泛化 | 去重/抽象 |
| **Skill Improve** | 用新经验精化技能 → 特化 | improve/refine |

> 踩坑：模型**自主生成技能**时常常收益有限甚至为负——因缺质量控制/精化/抽象机制。Create 之外必须有 Merge/Improve 治理闭环。

## 4.6 两种运行模式（决定怎么冷启动）

1. **蒸馏模式 Distillation**：用**强模型**抽经验建库，弱模型执行推理。扩展弱模型能力边界最直接的方式。
2. **自进化模式 Self-evolution**：抽经验的模型 = 执行模型，自我抽取、自我进化。

## 4.7 写入治理红线

> **语义记忆可后台自动抽取写入；程序性记忆（技能/playbook）必须经"审慎 promotion + 校验"写入——唯一永远不该全自动的写入路径。**
> 原因：程序性知识一旦错误会被 Agent"自动遵循"，污染面比一条错误事实大得多。

# 第五部分 记忆→Skill 生成（程序性记忆的极致）

> 承接第三部分 3.1 表格里的 ⑤/⑥：本部分聚焦 skill/代码这种程序性知识形式。它最硬核、最有价值，但**不代表知识只有 skill**——语义知识（事实/图谱/profile）同样重要，别顾此失彼。

这是"从使用记录学知识"最硬核的一支：不是存事实，而是把噪声原始记录蒸馏成**可复用、可验证、可组合的 skill**。

## 5.1 学术鼻祖：Voyager（2023，NVIDIA + Caltech，开源）

第一个"活到老学到老"的 skill library agent，在 Minecraft 里无人干预自动生成技能。

**三大组件：**

| 组件 | 作用 |
|------|------|
| 自动课程 automatic curriculum | 决定"下一步学什么"以最大化探索 |
| skill library | 不断增长的**可执行代码**技能库 |
| 迭代提示 iterative prompting | 环境反馈 + 执行错误 + 自我验证，反复精炼代码 |

**关键设计：用代码而非自然语言当 skill**——程序天然能表达时序延展、可组合的动作，长程任务必需；skill = 函数，用其描述的 embedding 索引。

**"记忆→skill"闭环：**
```
新任务 → 用「任务描述+环境反馈」embedding 检索 skill 库，取 top-5
      → 喂 LLM 复用/组合 → 生成新可执行程序
      → 执行拿环境反馈+执行错误 → 迭代精炼（多轮）
      → 自我验证（另一次 LLM 判断"是否真完成"）
      → 通过 → 作为新 skill 存回向量库
      → 能力随时间「复利」增长
```

三种反馈信号：**环境反馈**（程序能跑，世界反馈结果）、**执行错误**（程序非法）、**自我验证**（LLM 判断是否完成）。

**关键结果**：比前 SOTA 多拿 3.3x 物品、快 15.3x 到里程碑；去自我验证掉 73%；skill library 后期最关键；**可插拔迁移**——学的 skill 给 AutoGPT 用也能提升。

## 5.2 工程可用：Anthropic Agent Skills + Claude Dreaming

离生产最近且开源（Claude Code 本身在用）。

- **Agent Skills**（2025-12-18 发布为**跨平台开放标准**）：skill = 含 `SKILL.md` 的目录（YAML frontmatter：name+description + 指令/脚本/资源）。**渐进式披露**：启动只加载 name+description，用到才载全文。
- **skill-creator**（官方 skill）：交互式生成 skill 目录、`SKILL.md`、打包资源。
- **Claude Dreaming**（仿生物睡眠固化，**未正式发布**为自动特性）：Agent 自动回顾过往 session，识别重复/失败模式，把噪声日志蒸馏成高信号知识。最高级形态 = 把经验蒸馏成可泛化规则（最难最有价值）。**不改模型权重**，只作用于外部记忆层。
- **社区复刻** `grandamenium/dream-skill`：用 Claude Code 的 Stop hook，退出 session 时自动触发 `/dream` 固化。

## 5.3 第一环：skill 生成——从记录到一个可用 skill

skill 的生命周期分两大环：**生成**（本节，从零造出一个 skill）和**进化**（下节，让已有 skill 库越用越好）。两环都重要，先讲生成。给定一批使用记录，产出一个可复用 skill 的最小闭环：

```
① 采集轨迹     结构化留存 trajectory（含 user 意图 / 工具调用序列 / 参数 / 返回 / 成败信号）
       ▼
② 分组         按「任务类型」聚类同类轨迹（同一意图的多条记录放一起，跨轨迹才能分离"模式 vs 噪声"）
       ▼
③ 蒸馏抽取     喂 LLM：成功轨迹→抽「策略性步骤模式」；失败轨迹→抽「一句话教训」
              产出结构化草稿：{name, 触发条件 when-to-use, 步骤/代码, 输入输出, 注意事项}
       ▼
④ 规范化       写成标准载体：Voyager=可执行函数 / Anthropic=SKILL.md 目录 / 通用=playbook.md
              用 name+description 生成 embedding 建索引（供后续检索复用）
       ▼
⑤ 校验(必做)   staging/dry-run：候选 skill 先在副本环境跑，比对期望结果；不能只靠 LLM 自问"成了吗"
       ▼
⑥ promote     人工 review 或自动闸门通过 → commit 进 skill 库（带版本号）
```

**生成阶段最容易出的三个错**：
- 只喂单条轨迹让模型"总结成 skill"——单条噪声太大，必须**跨同类轨迹比对**才能提炼出可复用部分。
- 跳过 ③ 的失败轨迹——失败里的"局部教训"往往比成功轨迹更值钱（省掉整条试错）。
- 生成即入库——**没有 ⑤ 校验的自动生成，收益常为负甚至有害**（见 5.5）。

**冷启动技巧（SkillX 蒸馏模式）**：用**强模型**批量蒸馏历史记录建初版库，之后交给**弱模型**执行——这是扩展弱模型能力最省钱的路径。

## 5.4 第二环：skill 进化——让技能库越用越好

生成解决"从无到有造出一个 skill"，进化解决"库大了之后怎么不烂"。二者是**同等重要的两半**：只会生成、不会进化，库会越长越差（冲突、冗余、过时、token 暴涨、泛化下降）；只谈进化、没有生成，则无米下锅。规模化后手工精化不可行，必须自动化。

### 5.4.1 四种进化范式（按作用层级从小到大）

| 范式 | 作用层级 | 在做什么 | 代表 |
|------|---------|---------|------|
| **Execution feedback** | 单次运行、step 级 | 一次执行报错/成功 → 就地修正当前 skill 的一步 | Voyager 迭代提示 |
| **Trajectory distillation** | 多次运行、序列级 | 单条轨迹噪声太大 → **跨轨迹**提炼稳定可复用模式（进化的主力） | SkillRL、Mem^p |
| **Compression & augmentation** | 库级结构 | 去冗余、合并近义 skill、补缺失 skill | SkillComposer |
| **Reinforcement learning** | task 级 reward | 用任务成败作 reward，递归优化整库 | SkillRL |

### 5.4.2 库级治理三动作（进化的落地抓手）

对应第四部分 4.5 的 SkillComposer 三能力，是进化真正要跑的操作：

- **Merge 合并 → 泛化**：把语义相似的多个 skill 合成一个更通用的，去冲突、去冗余。库膨胀的主要解药。
- **Improve 精化 → 特化**：用新经验修正已有 skill（补边界条件、改错步骤、更新过时参数）。
- **Prune/Deprecate 淘汰**：过时/不安全/低命中的 skill 下架或标记失效——ReMe 的"策略性删除有害经验"就是这一步。**没有淘汰，库必烂。**

### 5.4.3 进化的两个红线

1. **失败诊断与重写分离**：把"诊断为什么失败"和"生成修正版"分成两步的系统，跨任务表现更强——别让模型一步既判因又改。
2. **进化写入同样不能全自动**：Improve/Merge 改的是程序性知识，一旦改错会被 Agent 自动遵循，污染面大。改动同样走 staging + 版本/回滚（见 5.5、7.3）。

> 一句话：**生成负责"长出新技能"，进化负责"修剪成材"，缺一不可。** 想直接上手的开源工具见第六部分程序性记忆层框架（6.A.10 upskill 生成、6.A.11 EvoSkill 进化）；全生命周期研究实现见 6.B（MUSE-Autoskill 覆盖 create/memory/mgmt/eval/refine 全环）。

## 5.5 记忆→Skill 的生产红线

1. **Voyager 自我验证不能直接搬真实业务**：Minecraft 太理想（即时报错、干净重置、无副作用、成功二元明确）；真实域（金融）一次 LLM 问"成功了吗"**不足以保证正确性**。必须加 **staging / dry-run**：候选 skill 先在副本执行验证，再 commit。
2. **写 skill 比写事实危险得多**（CoALA）：容易引 bug 或让 Agent 偏离设计意图。必须人工 review / promotion 闸门。
3. **自生成库会退化甚至变危险**：过时/不安全 skill 会把错误传播到下游；需持续诊断/维护/对齐，不能静态流水线。

## 语义记忆层框架

### 6.A.1 Mem0 —— 最快接入的个性化记忆

给任意 Agent（不限框架）外挂"记住用户偏好/事实"的能力。最小用法：

```python
from mem0 import Memory
m = Memory()                                     # 默认向量库；加 config 可切图/自定义 LLM
m.add(                                            # 从对话自动抽取事实并存
    [{"role": "user", "content": "我喜欢公制单位，住在阿姆斯特丹"}],
    user_id="alex",
)
m.search("用户住哪", filters={"user_id": "alex"})   # 语义检索，返回相关记忆片段
m.get_all(filters={"user_id": "alex"})            # 列出该用户全部记忆
```

**具体做法**：你把整段对话丢给它 `add`，它背后用一个 LLM 把对话里"值得记的事实"抽出来（"喜欢公制""住阿姆斯特丹"），再和已有记忆比对——**新事实就存、和旧的冲突就更新、重复就丢**（这步叫 memory decay/去重）。存的时候一条事实同时写进向量库（存语义）、可选图库（存实体关系）和 KV。下次 `search` 时按语义相似度捞回最相关的几条，拼进 prompt。核心卖点就是"你只管灌对话，记什么、去不去重它替你决定"。
- **何时触发**：由你的代码显式调 `add` 时触发（通常每轮对话后调一次），不是它自己在后台盯着。
- **是否需用户确认**：不需要。抽取、去重、覆盖全自动，写完即生效，中间没有人工审核步（要管控就得自己在 `add` 前后加逻辑）。

**安装与使用**

- 环境：Python 3.9+；PyPI 包名 `mem0ai`；许可证 Apache 2.0。默认要 `OPENAI_API_KEY`（可换本地模型/其它 LLM）。
- 两条路子：
  - **纯 SDK（最轻）**：`pip install mem0ai` 后直接 `Memory()`，向量库默认用内置的，零外部服务就能跑上面的最小 demo。要图能力则装带图后端的 extra 并在 config 里指定 Neo4j。
  - **自托管 server（要 REST/多语言/带面板）**：官方 server 是 FastAPI + Postgres(pgvector) + Neo4j 三容器。
    ```bash
    git clone https://github.com/mem0ai/mem0 && cd mem0/server
    make bootstrap        # 起全栈 + 建管理员 + 发第一个 API key；面板 http://localhost:3000
    ```
    > 注意：自托管 REST **没有 `/v1/` 前缀**（`POST /memories`），托管平台 api.mem0.ai 才有 `/v1/`；别照搬平台文档的路径。旧的 OpenMemory 正在退场，自托管统一走这个 server。

**集成方式（4 条路径）**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **Python/TS SDK** | `Memory()`(自托管) 或 `MemoryClient(api_key=)`(托管平台) 直接 `add/search` | 应用内嵌，任意框架 |
| **REST API** | 自托管 server 暴露 HTTP，`curl -X POST .../memories`，`/docs` 有 OpenAPI | 非 Python 栈、跨语言 |
| **MCP server** | 官方 MCP 连托管平台；自托管连本地栈可用社区实现（tensakulabs/elvismdev 等） | Claude Code / Cursor 等 MCP 客户端 |
| **托管平台** | 注册拿 key，零运维 | 不想管基础设施 |

### 6.A.2 Graphiti —— 时序知识图谱（自托管 Zep 的正解）

双时态：老事实不删除，只标 `invalid_at`，可查"某时间点当时为真的是什么"。适合客服/销售等**事实会随时间变化、且时间点正确性是产品一部分**的系统。最小用法：

```python
from graphiti_core import Graphiti
g = Graphiti("bolt://localhost:7687", "neo4j", "password")
await g.build_indices_and_constraints()
await g.add_episode(                              # 灌入一段对话/事件，自动抽实体关系、打时间戳
    name="chat-1", episode_body="Ken 上周把 HQ 从鹿特丹搬到了阿姆斯特丹",
    source_description="用户消息", reference_time=datetime.now(),
)
await g.search("Ken 的 HQ 在哪")                  # 混合检索，返回带 valid_at/invalid_at 的事实
```

**具体做法**：每灌一段对话/事件（叫一个 episode），它用 LLM 从里面抽出"实体 + 关系"画成图——比如从"Ken 把 HQ 从鹿特丹搬到阿姆斯特丹"抽出 `Ken —HQ位于→ 阿姆斯特丹`。关键在于它**不覆盖旧事实**：老的 `Ken —HQ位于→ 鹿特丹` 会被打上"失效时间(invalid_at)"，新的记上"生效时间(valid_at)"，两条都留在图里。所以你能查"今天 HQ 在哪"也能查"去年这时候 HQ 在哪"。检索是向量+图+全文混合。和 Mem0 的区别：Mem0 冲突就改写覆盖，Graphiti 冲突就存成一段带时间线的历史。
- **何时触发**：你显式 `await add_episode(...)` 时触发，每灌一段就抽一次图。
- **是否需用户确认**：不需要。抽实体关系、给旧事实标失效全自动。好在它**不删除**旧数据（只标失效），所以即便自动判断错了，历史也留着可追溯、可人工纠。

**安装与使用**

- 环境：Python 3.10+；PyPI `graphiti-core`；许可证 Apache 2.0。**必须有一个图数据库后端** + 一个支持结构化输出的 LLM（OpenAI/Anthropic/Gemini，小模型易抽错）。
- 后端二选一：
  - **Neo4j 5.26+**：`pip install graphiti-core`，连 `bolt://localhost:7687`。
  - **FalkorDB**（Redis 系，更轻）：`pip install "graphiti-core[falkordb]"`。
- 起后端最快用 Docker，例如 Neo4j：
  ```bash
  docker run -p 7474:7474 -p 7687:7687 \
    -e NEO4J_AUTH=neo4j/password neo4j:5.26
  export OPENAI_API_KEY=sk-xxx
  # 然后跑上面的 Python 最小 demo：build_indices → add_episode → search
  ```

**集成方式**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **Python SDK** | `Graphiti(...)` 直接 `add_episode/search`（上面 demo） | 应用内嵌 |
| **MCP server** | 仓库 `mcp_server/` 带官方实现，`docker compose up` 同时起 Neo4j + MCP（HTTP transport，端口 8000，暴露 `add_episode`/`search_facts`/`search_nodes`） | Claude Code / Cursor 等；Claude Desktop 因只认 stdio 需 `mcp-remote` 网关 |
| **REST/其它** | 通过 MCP 或自己在 SDK 外面包一层 HTTP | 跨语言 |

### 6.A.3 Cognee —— 一体化图+向量记忆引擎

`add → cognify → search` 三步（`prune` 清理），单 Postgres 可跑图+向量+session。适合想要图化决策、一体化部署、从纠错改进的团队。最小用法：

```python
import cognee, asyncio
async def main():
    await cognee.add("Ken 偏好公制，HQ 在阿姆斯特丹")   # 灌数据
    await cognee.cognify()                              # 构建知识图谱+向量索引（核心步骤）
    print(await cognee.search("Ken 的偏好"))            # 检索
asyncio.run(main())
```

**具体做法**：分两步——`add` 先把原始资料（对话、文档、代码）囤进来不加工；`cognify` 才是重头戏，它跑一条 LLM 流水线把这些原料**同时**加工成知识图谱（实体关系）和向量索引，并把两者关联起来。也就是"先进货、再统一加工上架"。`search` 时图和向量一起查，既能语义召回又能顺着关系多跳推理。相比 Mem0/Graphiti 一条条增量抽取，Cognee 更像"给你一整套 ETL 管道 + 单 Postgres 全栈存储"，适合把成批文档一次性图谱化。
- **何时触发**：**两段式、由你手动控制**——`add` 只入库不加工，要等你显式调 `cognify` 才真正建图建索引。所以可以攒一批再统一处理，不是每句话即时抽。
- **是否需用户确认**：不需要人工审核，但"何时加工"这个开关在你手里（调不调 `cognify` 你说了算），比 Mem0/Graphiti 每次 add 就自动抽多一层批处理的可控性。

**安装与使用**

- 环境：Python 3.10+；PyPI `cognee`；许可证 Apache 2.0。要 `LLM_API_KEY`。默认可用本地文件/嵌入式后端起步，生产可切单 Postgres（图+向量+session 全放一处）。
  ```bash
  pip install cognee
  export LLM_API_KEY=sk-xxx
  # 跑上面 demo：add → cognify → search；清库用 await cognee.prune()
  ```
- 除 `add/cognify/search/prune`，还有 `codify`（把代码仓库建成 code graph）。

**集成方式**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **Python SDK** | `import cognee` 直接 `add/cognify/search`（上面 demo，异步） | 应用内嵌 |
| **MCP server** | 仓库带 `cognee-mcp`，支持 stdio/SSE/HTTP 三种 transport；Claude Code 一行接入 `claude mcp add --transport http cognee http://localhost:8000/mcp -s project`，暴露 `cognify`/`codify`/`search`/`prune` 等工具 | Claude Code / Cursor 等 |
| **REST(API 模式)** | 先起 Cognee FastAPI server，再让 MCP 指向它（`API_URL`+`API_TOKEN`） | 已有服务端、跨语言 |

### 6.A.4 LangMem —— LangGraph 生态内的记忆

适合**已经在用 LangGraph/LangChain** 的项目，原生集成、无额外服务。两类用法：工具挂载（agent 自主增删查）+ 后台 memory manager（异步抽取合并）。

**具体做法**：它不另起服务，而是给你的 LangGraph agent 挂两类东西。一是**工具**（`manage_memory` / `search_memory`）——让 agent 在对话中自己决定"这条要记"就调工具写进去、"需要旧信息"就调工具搜出来（主动式，像 Letta 那样 agent 自管）。二是**后台 memory manager**——你把对话丢给它，它异步用 LLM 抽取事实、去重合并，你不用手动触发（被动式，像 Mem0 那样）。两种模式可以混用。存储走 LangGraph 的 store（可 namespace 隔离用户）。核心卖点是"你已经在 LangChain 生态里，加记忆不用引第三方服务"。
- **何时触发**：取决于你用哪种模式。工具模式——**agent 自己在对话里判断该记就调**（时机不固定，看模型决策）；manager 模式——你把对话喂给它就异步抽（可放对话结束后批量跑）。
- **是否需用户确认**：默认都不需要人工确认。但工具模式给了个天然插点：因为写记忆是一次 tool call，你可以像审别的工具调用一样，在 agent 真正写入前加一道人工审批（human-in-the-loop）。manager 模式则是纯自动。

**安装与使用**

- 环境：Python 3.10+；PyPI `langmem`；许可证 MIT。**不起独立服务**，作为库嵌进 LangGraph 应用。记忆落在 LangGraph 的 store 上（开发用内存 store，生产用带持久化+向量的 store，如 Postgres）。
  ```bash
  pip install -U langmem
  export OPENAI_API_KEY=sk-xxx
  ```
  ```python
  # 最小可跑：给 store 配好后，把两个工具挂到 create_react_agent
  from langgraph.prebuilt import create_react_agent
  from langgraph.store.memory import InMemoryStore
  from langmem import create_manage_memory_tool, create_search_memory_tool
  store = InMemoryStore(index={"dims": 1536, "embed": "openai:text-embedding-3-small"})
  agent = create_react_agent("openai:gpt-4o-mini",
      tools=[create_manage_memory_tool(namespace=("memories",)),
             create_search_memory_tool(namespace=("memories",))], store=store)
  ```

**集成方式**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **工具挂载（主动）** | `manage_memory`/`search_memory` 挂给 agent，模型自己增删查（可加 human-in-the-loop 审批） | LangGraph agent 内 |
| **后台 manager（被动）** | `create_memory_manager(...)` 喂对话异步抽取合并 | 对话后批量固化 |
| **store 层复用** | 记忆直接读写同一个 LangGraph store，可 namespace 按用户隔离 | 已有 LangGraph 持久化栈 |

> 无 REST/MCP/独立服务——它的"集成"就是深度长进 LangGraph 生态，这既是省事也是绑定。

### 6.A.5 记忆 OS 家族：Memobase / MemoryOS / MemOS

三个 2025-2026 新起的框架，都真开源、有 pip 包。前两个偏纯语义，MemOS 已延伸到程序性（跨任务 skill 复用），是通往下一小节的过渡。三者一句话区分：**Memobase** 最轻，只做"用户画像+时间线"，适合陪伴/教育/个性化助手；**MemoryOS**(BAI-LAB) 借鉴 OS 内存管理分四模块，长期对话基准最强；**MemOS**(MemTensor) 主打自进化 + 跨任务 skill 复用，语义与程序性兼备。

**具体做法**：三个都借了操作系统"分层管内存"的思路，但侧重不同。
- **Memobase**：你把对话 `insert` 进去，它后台异步把这个用户的零散对话**汇总成一份结构化用户画像**（年龄/偏好/职业…这类字段）+ 一条**事件时间线**。你要用的时候 `profile()` 直接拿这份画像，只走几条 SQL 所以快（<100ms）。就是"把散对话压成一张用户档案卡"。
- **MemoryOS**(BAI-LAB)：把记忆分成短期/中期/长期三层，像操作系统换页一样，聊得多了就把重要内容从短期"固化"到长期、不重要的淘汰掉，靠存储/更新/检索/生成四个模块协作。主打超长对话不丢关键信息。
- **MemOS**(MemTensor)：把记忆统一成图结构，除了存事实还能**把"怎么做某类任务"沉淀成可跨任务复用的 skill**，并让记忆随使用自我进化——所以它一只脚已经跨进程序性记忆层了。

- **何时触发 & 是否需确认**：三个都是"你灌数据 → 它后台异步加工"，加工时机由框架自动调度、不需要你逐条触发，也**默认不需要用户确认**（Memobase 攒够对话就异步更新画像；MemoryOS 聊到一定量就自动把短期固化进长期；MemOS 随使用自我进化）。代价是自动化程度越高、越难人工把关——MemOS 因为会自动沉淀 skill 并自进化，若用在生产，建议对它写出的程序性记忆按第五部分红线加一道 staging/人工 promote，别让它全自动改。

**安装与使用（三个分别说，注意命名撞车）**

- **Memobase**：PyPI `memobase`（Python）+ TS SDK；后端是 FastAPI + Postgres，最省事用 Docker：
  ```bash
  git clone https://github.com/memodb-io/memobase && cd memobase/src/server
  docker compose up -d          # 起服务，默认 http://localhost:8019
  pip install memobase          # 客户端；再跑上面的 add_user→insert→profile demo
  ```
- **MemoryOS**(BAI-LAB)：`pip install MemoryOS-BaiJia`（⚠️ 包名带 `-BaiJia`），给 add/retrieve/生成配 LLM key 即用；也提供 MCP server 版本供 Claude/Cursor 接。
- **MemOS**(MemTensor)：`pip install MemoryOS`（⚠️ 项目叫 MemOS 但包名是 `MemoryOS`），可选 extra `[tree-mem,mem-reader,mem-scheduler]`；统一 `add/search/edit/delete` API，需图/向量后端 + LLM key。

**集成方式**

| 框架 | SDK | 服务/协议 | 备注 |
|------|-----|----------|------|
| **Memobase** | Python / TS SDK | 自托管 REST（FastAPI，:8019）；亦有托管云 | 挂给任意 LLM app 加"记住这个用户" |
| **MemoryOS**(BAI-LAB) | Python SDK | **MCP server**（接 Claude Code/Cursor） | 长对话个性化，四模块可分别调 |
| **MemOS**(MemTensor) | Python SDK | 统一记忆 API + 可选调度器组件 | 语义+程序性兼备，生产建议对 skill 写入加人工 promote |

### 6.A.6 Agent-Wiki 家族 —— 编译式知识库（ingest 时处理，而非 query 时检索）

上面几个把语义记忆存成向量/图/画像卡；Agent-Wiki 走的是**另一种范式：知识编译（knowledge compilation）**——源自 Andrej Karpathy 提出的 LLM Wiki 模式，核心信条是**在 ingest（导入）时就把知识处理成结构化 wiki 页面，而非在 query 时才检索碎片**。这是第三部分"markdown 文件"存储形式 + 第四部分"蒸馏/固化"主线的另一种落地：不是存原始 chunk 等用时捞，而是导入时就蒸馏成实体页/概念页 + 交叉引用，知识随增长**复利式交叉引用**而非线性堆叠。

**与 RAG 的本质区别**（选它而非传统向量 RAG 的核心理由）：

| 维度 | RAG | Agent-Wiki |
|------|-----|-----------|
| 知识组织 | 原始 chunk 向量化 | 编译为结构化 wiki 页面 |
| 查询时 | 每次检索 + 拼装 | 直接读取编译后的知识 |
| 知识增长 | 线性堆叠 | 复利式交叉引用 |
| 矛盾处理 | query 时才暴露 | ingest 时即标记 |
| 准确率 | ~63%（相同检索预算） | ~89%（agentwikis.com 公开数据） |

**生态有三个相关但不同的项目**，同属"编译式 wiki"理念、工程形态各异；按离 coding agent 的距离排序。

#### 6.A.6a `@agent-wiki/mcp` —— 个人/项目级，MCP 接入最直接

- **定位**：纯 Markdown + SQLite FTS5 的 MCP Server，提供 15 个 wiki 工具，原生支持 Claude Code / Cursor / Windsurf。**离 coding agent 最近、最适合个人和项目级知识管理**的实现。
- **具体做法**：编译器式**三层不可变架构**——
  - `raw/` 源层：write-once，SHA-256 校验，作 ground truth 永不修改；
  - `wiki/` 知识层（可变）：编译产物，含实体页 entities/、概念页 concepts/、源摘要 sources/、合成页 syntheses/；
  - `synthesis/` 合成层：overview.md 等跨源高阶理解，每次 ingest 自动修订。

  ingest 时跑完整管线：`Ingest（写 raw/）→ Entity Extract（自动识别人物/公司/项目/概念）→ Wiki Page Compilation（建/更实体页+概念页、注入 [[wikilink]]、每个 claim 带 provenance 回溯源）→ Synthesis Revision（新源与已有知识矛盾时**即时标记**）→ Index Update（FTS5 全文 + 向量索引 MiniLM-L6-v2 + 知识图谱 build）`。
  - **混合搜索**：`score = α·BM25 + (1-α)·cosine`（embedding 用 Xenova/all-MiniLM-L6-v2 ~90MB，首次自动从 HuggingFace 下载缓存；embedding 失败自动降级纯 BM25，查询永不失败）。
  - **知识图谱（双遍扫描）**：Pass 1 解析 `[[wikilink]]` 生成确定性 EXTRACTED 边；Pass 2 语义相似度推理带置信度的 INFERRED 边；社区检测聚类相关主题；输出 Mermaid/DOT/JSON + 3D force-graph 可视化。
  - **质量保证两层**：`health`（结构性检查：空文件/index 同步/目录完整性，每次 session 前跑，**不依赖 LLM**）+ `lint`（内容质量：孤立页/断链/缺实体页/语义矛盾/数据缺口与补源推荐，每 10-15 次 ingest 跑一次，**依赖 LLM**）。
- **何时触发**：显式调 `wiki_ingest` 触发编译全流程；`wiki_search`/`wiki_read` 按需查已编译知识；`wiki_health` 每次 session 前跑、`wiki_lint` 周期跑。
- **是否需用户确认**：ingest/编译默认自动；但 wiki 就是明文 markdown（可 git 管），人可随时直接改。**矛盾在 ingest 阶段即标记**而非隐藏到 query——把"知识一致性检查"前置到导入环节，是这个范式最关键的设计。
- **两种运行模式**：In-Wiki（wiki 作独立知识仓库）和 Second-Brain（`.wiki/` 嵌入现有项目作共享记忆）。
- **安装与使用**：

  ```bash
  npm install -g @agent-wiki/mcp
  agent-wiki install claude-code        # 装 Claude Code 原生 skill，得 /wiki-ingest /wiki-search 等 slash command
  ```
  MCP 配置（Claude Code `~/.claude/settings.json` / Cursor `.cursor/mcp.json`；⚠️ VS Code 根 key 用 `"servers"` 而非 `"mcpServers"`）：
  ```json
  { "mcpServers": { "agent-wiki": { "command": "npx",
    "args": ["-y", "@agent-wiki/mcp", "serve", "--wiki-path", "/path/to/knowledge"] } } }
  ```
  CLI 直调：`npx @agent-wiki/mcp call wiki_search '{"query":"deployment"}'`；3D 图谱可视化：`agent-wiki web --wiki-path ./wiki --open`。还支持**语言插件**对源码做确定性解析（无需 LLM）建跨文件 code graph，适合给代码库建可维护知识文档。

- **集成方式**：

  | 路径 | 怎么用 | 适合 |
  |------|--------|------|
  | **MCP Server** | npx 起 serve，15 个 wiki_* 工具（read/write/search/list/ingest/graph/suggest/lint/health…） | Claude Code / Cursor / Windsurf / 任意 MCP 客户端 |
  | **Claude Code skill** | `agent-wiki install claude-code` → slash command | 偏好命令式的 Claude Code 用户 |
  | **CLI 直调** | `npx @agent-wiki/mcp call <tool> '<json>'` | 脚本、CI |
  | **语言插件** | 确定性解析源码建 code graph，带 provenance 回溯源文件 | 给代码库建知识文档 |

#### 6.A.6b `llm-wiki-agent` —— Python 实现，Claude Code 原生 skill

- **定位**：同一 LLM Wiki 理念的 Python 实现（SamurAIGPT，3.2k stars）。接入方式是 Claude Code native skill / AGENTS.md（非 MCP），搜索基于 LLM 语义检索（非 BM25+向量混合），图谱是 2D graph.html（非 3D），健康检查集成式（非 health/lint 分离），兼容 Claude Code / Codex / OpenCode / Gemini CLI。
- **使用**：clone 仓库后按 CLAUDE.md 在 Claude Code 中用 `/wiki-ingest`、`/wiki-search`、`/wiki-graph`。

#### 6.A.6c Onyx Agent-Wiki —— 团队协作版 self-updating wiki webapp

- **定位**：上面 a/b 偏个人/项目级；Onyx 版（onyx-dot-app，2026 年中新出）偏**多人多 agent 共维的团队共享知识库**，是带 Web UI 的完整应用（非 pip/npm 库）。设计信条三句话：agent 协作最好的文档格式是 Markdown、最好的层级表示是文件系统、最好的历史管理是 Git。
- **三个核心机制**（正好印证本文档两条主线）：
  - **Update Policy（更新策略）= 写入治理红线的产品化**：每个页面/文件夹可挂更新策略——可**关掉自动更新**防止外部 ingestion 覆盖，可写**自然语言更新约束**（如"条目保持精简""永远别动 SLA 表"）让 updater agent 遵守；策略沿目录树**继承**，子页面可覆盖父级。这就是第五部分"程序性/语义记忆写入不全自动、人可加约束"红线的现成实现。
  - **Triggers（触发器）**：用自然语言声明关心什么（"某项目状态从绿转黄时触发""projects/ 下落地新设计文档时触发"），scope 到具体文件/目录。
  - **事件投递**：事件进 event log，可调 API / 轮询 / webhook 推给下游系统或 agent，串起工作流；支持 K8s（Helm + Terraform for EKS）。
- **何时触发**：由外部来源推送（ingestion）或 Trigger 命中时触发 updater agent 去改对应页面——事件驱动，不是你手动逐条调。
- **是否需用户确认**：**Agent-Wiki 家族里唯一把"确认/管控"做成一等公民的**。默认可自动改，但每页/每目录可通过 Update Policy **关掉自动更新**（那样就只能人工改）或加自然语言约束限制 agent 怎么改；加上每次改都是 git commit，可 diff、可回滚。等于把"是否需要人确认"从代码层面提到了产品配置层面。
- **安装与使用**：带 Web UI，靠 Docker 起。之后在 UI 里建目录/页面、为每页配 Update Policy、写 Trigger。

  ```bash
  # 方式一：一条命令拉起
  curl -fsSL https://raw.githubusercontent.com/onyx-dot-app/agent-wiki/main/install.sh | bash
  # 方式二：克隆自起
  git clone https://github.com/onyx-dot-app/agent-wiki && cd agent-wiki
  docker compose up -d
  # 打开 http://localhost:8090，注册第一个账号即成管理员
  ```

- **集成方式**：

  | 路径 | 怎么用 | 适合 |
  |------|--------|------|
  | **Web UI** | 人直接读写 wiki、配策略与触发器 | 团队日常协作 |
  | **Ingestion 推送** | 外部来源（对话/系统）把内容推进来，updater agent 按策略改页 | 让 agent 持续喂养知识库 |
  | **Trigger + 事件投递** | 命中触发 → event log → 调 API / 轮询 / webhook 推下游 agent 或 workflow | 事件驱动的自动化编排 |

> **三个怎么选**：个人/项目级、已用 MCP → `@agent-wiki/mcp`；已用 Claude Code、偏好 Python 生态 → `llm-wiki-agent`；团队协作、需 Web UI + 事件系统 + 精细"谁能改哪页"治理 → Onyx。三者都不适合当纯后台向量记忆层（那用 Mem0/Cognee）。
> 深度解读见同目录 **`Agent-Wiki.md`**（编译器式三层不可变架构、ingest→extract→compile 管线、双遍扫描知识图谱、BM25+cosine 混合搜索、health/lint 双层质检、三个项目对比）。

## 程序性记忆层框架（含 skill 生成）

> 上面几个主打"存事实"；下面几个主打"存怎么做"——从 agent 自管记忆块，到直接从记录生成可复用 skill。这就是第五部分"记忆→skill"的落地工具，和语义层框架是**同一记忆系统的另一层**，不是两套东西。

### 6.A.7 Letta —— agent 自管记忆的完整运行时

完整运行时（不是纯记忆层）：agent 把自己的记忆当"操作系统内存"自管，适合长期个人助理、需持续演进用户画像。**注意框架锁定**。最小用法：

```python
from letta_client import Letta
client = Letta(base_url="http://localhost:8283")
agent = client.agents.create(
    model="openai/gpt-4o-mini",
    memory_blocks=[{"label": "persona", "value": "我是助手"},
                   {"label": "human",   "value": "Name: Ken"}],
)
client.agents.messages.create(agent_id=agent.id,
    messages=[{"role": "user", "content": "记住我喜欢公制单位"}])
# 你不直接调记忆函数——Agent 在自己的 loop 里自编辑 core/recall/archival
```

**具体做法**：Letta 把 agent 的记忆当"操作系统内存"来管。它给 agent 几块常驻 prompt 的**记忆块**（memory block，比如 `persona` 记自己是谁、`human` 记用户是谁），外加装不下时换出去的归档区。关键是**agent 自己编辑自己的记忆**——你只管发消息，agent 在推理 loop 里判断"这条得记进 human 块""这块满了得摘要归档",然后调内置的记忆函数（`core_memory_append`/`replace`、`archival_insert` 等）自行写入。你不直接调记忆 API。所以它存的不只是事实，还包括"我该怎么跟这个用户打交道"这类程序性经验，能跨 session 继承。
- **何时触发**：agent 在每轮对话的推理中自己决定何时读写记忆（模型驱动，时机不固定），不是你的代码或后台定时触发。
- **是否需用户确认**：默认不需要，agent 自主编辑。风险也在这——记什么全靠模型的 tool call 决策，模型没调保存工具就永久丢失、调错就写脏。要管控只能靠选强模型 + 在 ADE（可视化后台）里事后检查/纠正它的记忆决策，没有内建的"写入前人工审批"闸。

**安装与使用**

- 环境：许可证 Apache 2.0。它是**完整运行时/服务**，不是纯库——后端 FastAPI + Postgres 管 agent 状态。要 LLM key（`OPENAI_API_KEY` 等）。
- 起服务两种：
  - **Docker（推荐）**：挂持久化卷、暴露 8283。
    ```bash
    docker run -v ~/.letta/.persist/pgdata:/var/lib/postgresql/data \
      -p 8283:8283 -e OPENAI_API_KEY="你的key" letta/letta:latest
    ```
  - **pip**：`pip install letta`，起本地 server 后 SDK 连 `http://localhost:8283`。
- 关键点：你只定义**起始 memory blocks + 模型**，之后 agent 在自己的 loop 里自编辑记忆，**你不直接调记忆函数**（见 demo 注释）。

**集成方式**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **Python/TS SDK** | `Letta(base_url=...)` → `agents.create` / `messages.create`（上面 demo） | 应用内嵌 |
| **REST API** | server 暴露 HTTP，跨语言调 agent | 非 Python 栈 |
| **ADE（可视化后台）** | 浏览器里建/调 agent、逐层查记忆块、看 tool call、事后纠错 | 调试自主 agent 的记忆决策 |

> 注意**框架锁定**：Letta 是完整运行时而非可插拔记忆层——用它的记忆就得让 agent 跑在 Letta 里。深度解读见同目录 **`Letta.md`**（MemGPT 分页原理、Sleeptime agent、Split-Thread 架构）。

### 6.A.8 ReMe —— 文件式、可移植、程序性记忆专注

把记忆当**可读可编辑可移植的文件**；动态程序性记忆，能**策略性删除"有害经验"**（学到错的能反删）。

**具体做法**：ReMe 起一个本地服务，把 agent 的经验存成**可读可编辑的文件**（不是黑盒向量库）。它的循环是 "Remember Me, Refine Me"——用完一段任务，把这次的做法/教训 `Remember` 进去；后台再 `Refine`：把零散经验蒸馏合并成更稳的条目。最有辨识度的一点是**能反向删除"有害经验"**：如果发现之前学到的某条做法其实是错的（老让 agent 踩坑），可以策略性地把它从记忆里删掉，而不是只增不减。存成文件所以能直接翻、直接改、直接搬到别的项目。
- **何时触发**：`Remember` 由你在任务结束时显式调（CLI/API/MCP/SDK 都行）；`Refine`（蒸馏合并）是后台任务，可定期跑。
- **是否需用户确认**：写入/精化默认自动，但因为**记忆就是明文文件**，人可以随时打开审、改、删——审核门槛极低。它主打的"删除有害经验"本身既可以是策略自动触发，也可以人工介入决定删哪条，比纯自动追加的框架多一层可治理性。

**安装与使用**

- 环境：Python 3.11+；PyPI `reme-ai`；许可证 Apache 2.0。**基础功能（文件读写 + BM25 + wikilink 检索）无需任何 API key**，只有 LLM 驱动的记忆进化/语义检索才配 `LLM_API_KEY`。
  ```bash
  pip install "reme-ai[core]"        # 或源码：git clone ... && pip install -e ".[core]"
  reme start                         # 起本地服务，默认 127.0.0.1:2333
  # 五分钟 demo：reme write path=... → reme search query=... → reme read path=...
  ```

### 6.A.9 OpenViking —— 上下文数据库 + viking:// 文件系统

Agent 用 `ls`/`grep` 浏览上下文，三层分级加载；`skills/` 目录支持自进化。核心 AGPLv3，商用注意许可证。适合要文件式透明、可 grep 的记忆。

**具体做法**：OpenViking 把 agent 的全部上下文做成一个**类文件系统**（`viking://` 路径），agent 像在 shell 里一样用 `ls`/`grep` 浏览、按需三层分级加载（不是一次性全塞进 prompt）。程序性经验放在一个专门的 `skills/` 目录里，会**自进化**——agent 反复做某类任务时，把稳定下来的做法沉淀成该目录下的 skill 文件，下次直接 grep 出来复用。核心卖点是"记忆全程可 `ls`/`grep` 看得见"，透明、可审计，不像向量库那样是黑盒。
- **何时触发**：分级加载在 agent 每次要用上下文时按需触发；`skills/` 的沉淀/进化在反复执行同类任务过程中发生。
- **是否需用户确认**：默认自动沉淀，但因为一切都是文件、可 `ls`/`grep`/直接编辑，人工审查和干预非常容易——和 ReMe 类似，靠"明文文件"而非"审批闸"来实现可控。注意核心 AGPLv3，商用前先过许可证。

**安装与使用**

- 环境：Python（主体）+ 内置 Rust 打的 `ov` CLI；许可证**主项目 AGPLv3、CLI Apache 2.0**（商用先过许可证）。支持 Volcengine/OpenAI/Kimi/GLM/本地 Ollama 等 provider。
  ```bash
  pip install openviking --upgrade
  openviking-server init        # 向导：配 provider/模型，写 ~/.openviking/ov.conf
  openviking-server doctor      # 校验配置
  openviking-server             # 启动服务（后台：nohup openviking-server &）
  # 服务起来后用 ov CLI：
  ov status
  ov add-resource https://github.com/volcengine/OpenViking --wait
  ov ls   viking://resources/           # 像文件系统一样浏览
  ov find "what is openviking"          # 检索
  ov grep "openviking" --uri viking://resources/...
  ```

**集成方式（插件 / MCP / Hook / CLI，支持 10+ Agent）**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **插件 / Hook** | 装到 Claude Code / Codex / Cursor / Trae / OpenCode，自动注入召回 + **会话结束自动 commit 记忆** | 主流 coding agent |
| **MCP server** | 任意 MCP 客户端接入 | 通用 |
| **`ov` CLI / HTTP** | 脚本里 `ov find/grep/add-resource` | 自动化、可调试检索轨迹 |
| **Studio（免安装）** | 浏览器托管实例 openviking.ai/studio：上下文 playground、可视化配本地 agent、检查会话轨迹 | 快速试用/调试 |

> 深度解读（viking:// 三层 L0/L1/L2 分级加载、skills 自进化、与 ReMe 对比）见同目录 **`OpenViking.md`**。

### 6.A.10 upskill（HF）—— 从 trace 生成并评估 skill

程序性层最直接的"记忆→skill"工具：用**强模型**从任务或已有轨迹生成 skill，再在**弱模型**上评估——正是第五部分 5.3 生成管线的现成实现。为 coding agent（Claude Code / Codex / OpenCode）设计。产物是标准 `./skills/{name}/` 目录（SKILL.md 格式），**直接可挂给 Claude Code 等**；内建"生成→评估→精化(max_refine_attempts)"闭环，天然带 5.3 里的 ⑤ 校验环节。

**具体做法**：你给一句任务描述、或一条已经跑过的轨迹文件（`--from trace.md`），upskill 用一个**强模型**把"这类任务该怎么做"蒸馏成一个 `SKILL.md`（标准 skill 目录格式）。生成完不是就完事——它会拿一个**弱模型**去实际执行这个 skill 打分（`upskill eval`，多次 run 求统计显著性），不合格就自动精化重写（`max_refine_attempts`）。也就是把第五部分 5.3 的"生成→校验→精化"整条管线打包成 CLI。"强模型写、弱模型考"是它的招牌——保证产出的 skill 连弱模型都能照着做对。
- **何时触发**：**离线、人主动跑 CLI 触发**（`upskill generate` / `eval`），不是在线自动学。适合把一批历史轨迹拿来批量提炼成 skill 库。
- **是否需用户确认**：产物是 `SKILL.md` 文件，生成后**默认不会自动挂到你的 agent 上**——你 review 这个 markdown、觉得行了再手动放进 agent 的 skills 目录。这正是第五部分红线"程序性记忆经人工 promote 才生效"的现成实现：生成自动、上线要人点头。

**安装与使用**

- 环境：Python 3.13+；PyPI `upskill`（HuggingFace 出品）。按用到的模型配 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`（可配自定义 endpoint 走本地模型）。
  ```bash
  pip install upskill
  export ANTHROPIC_API_KEY=sk-xxx
  upskill generate "写规范的 git commit message"              # 从任务描述生成
  upskill generate "文档化这个模式" --from ./trace.md          # 从轨迹蒸馏（记忆→skill）
  upskill generate "解析发票" --model sonnet --eval-model haiku # 强生成、弱评估
  upskill generate "补错误处理示例" --from ./skills/api-errors/ # 改进已有 skill（自动识别目录）
  upskill eval ./skills/my-skill/ -m haiku -m sonnet --runs 5   # 多模型基准+统计显著性
  ```
- 远程跑：`--executor jobs --artifact-repo ...` 把生成/评估丢到 HuggingFace Jobs。

**集成方式**

| 路径 | 怎么用 | 适合 |
|------|--------|------|
| **CLI** | `upskill generate / eval`，离线批量提炼 | 从历史轨迹造 skill 库 |
| **产物挂载** | 产物是标准 `./skills/{name}/`（SKILL.md 格式），**人 review 后**手动放进 Claude Code / Codex / OpenCode 的 skills 目录 | 把 skill 上到 coding agent |
| **HF Jobs** | `--executor jobs` 远程执行 | 重任务、CI |

### 6.A.11 EvoSkill —— 从失败轨迹进化 coding agent 技能

对应第五部分 5.4「进化」环：从**失败轨迹**自动发现并合成 skill，用进化循环（提变异→held-out 评估→保留最优）迭代整个 agent 程序，git 分支全程可复现。特色：**生成 + 进化一体**，failures 驱动改进，维护 top-N 程序前沿。

**具体做法**：upskill 偏"从一条轨迹生成一个 skill",EvoSkill 偏"用一批**失败**轨迹进化整个 agent"。它跑一个进化循环：观察 coding agent 哪些任务失败 → 从失败里发现"缺了什么 skill / prompt 哪里不对" → 提出变异（新增/改写 skill、调 prompt）→ 在 held-out 任务集上评估 → **只保留跑分更高的**，维护一个 top-N 的"程序前沿"，一代代迭代。整个过程走 git 分支，每次变异都是一个可复现、可回滚的 commit。对应第五部分 5.4「进化」环。
- **何时触发**：人跑 `evoskill run` 启动进化循环（离线、批量、可能跑很久），不是在线随对话即时学。
- **是否需用户确认**：进化过程内部**用 held-out 评估自动当"守门员"**——变异必须评分更高才留下，等于用自动评估代替了部分人工把关。加上全程 git 分支可 diff、可回滚，人可以在合并进主线前 review 这一代的改动。所以是"自动筛选 + git 可审"的组合,比 Letta 那种纯模型自主更可控。

**安装与使用**
- 环境：Python **3.12+**；Apache 2.0；出品方 sentient-agi。不绑定特定模型，支持任意 provider（Anthropic / OpenAI / OpenRouter / Fireworks…），按用到的模型配对应 `*_API_KEY`。
- 安装：一行脚本装，或克隆后跑 `install.sh` 并指定要挂到哪些 coding agent：

  ```bash
  # 方式一：一键脚本
  curl -fsSL https://raw.githubusercontent.com/sentient-agi/EvoSkill/main/install.sh | bash

  # 方式二：克隆源码，指定接入的 agent
  git clone https://github.com/sentient-agi/EvoSkill && cd EvoSkill
  ./install.sh --agents claude,opencode
  ```

- 最小流程：`init` 建工作区 → `run` 启动进化循环（会跑很久，离线批量），产物是给 coding agent 长出的 skill + 优化后的 prompt，全走 git 分支：

  ```bash
  evoskill init                      # 初始化工作区（含 git 仓）
  evoskill run                       # 观察失败→变异→held-out 评估→保留最优
  evoskill run --agents claude       # 只针对某个 agent 进化
  git log --oneline                  # 每代变异都是一个可复现 commit
  ```

- 无独立服务/端口：EvoSkill 是**离线进化工具**，跑完把 skill 与 prompt 落到目标 coding agent 的配置里，不常驻。

**集成方式**

| 路径 | 怎么用 | 说明 |
|------|--------|------|
| **CLI 进化** | `evoskill init` / `evoskill run` | 主入口，离线批量进化整个 agent 程序 |
| **接入 coding agent** | `install.sh --agents claude,opencode` | 把进化出的 skill/prompt 直接挂到 Claude Code / OpenCode 等 |
| **git 分支** | `git diff` / `git revert` | 每代变异一个 commit，合并前可 review、可回滚 |
| **任意 provider** | 配 `*_API_KEY` | 进化与评估用的模型可自由切换 |

### 6.A.12 SkillWeaver —— web agent 自探索合成 skill 为 API

给一个新网站，agent 自主探索、练习、把经验蒸馏成健壮的 **API 式 skill**。WebArena 成功率相对提升 31.8%，强 agent 合成的 API 给弱 agent 用可提升 54.3%（跨 agent 迁移）。定位偏 web 自动化域；可复现、可迁移，工程化介于产品与论文之间。

**具体做法**：专攻 web agent。丢给它一个新网站，agent **自主去点、去试、去探索**这个站怎么操作，把摸索出来的稳定操作序列蒸馏成一个个**API 式 skill**（像给这个网站封了一层函数：`search_product(x)`、`add_to_cart(id)`），存进 skill 库供后续任务直接调。妙处在跨 agent 迁移——**强 agent 探索合成的 API，给弱 agent 用能大幅提分**（+54.3%），相当于强者探路、把路径固化成工具给弱者复用。
- **何时触发**：探索/合成阶段离线跑（给新站先自主练一遍），之后执行任务时按需调已合成的 skill。
- **是否需用户确认**：合成的 skill 是可复现、可迁移的产物，可在正式用于任务前 review；工程化介于产品与论文之间，生产用需自己补治理。要更泛化的"把任意轨迹归纳成 workflow 记忆"（不限 web），见 6.B 的 AWM。

**安装与使用**
- 环境：源码运行（OSU-NLP-Group 出品，偏研究工程），按 README 装 Python 依赖；配所用 LLM 的 `*_API_KEY`（如 `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`）。web 探索依赖浏览器自动化（Playwright 类），首次需装浏览器内核。
- 安装：克隆仓库，装依赖：

  ```bash
  git clone https://github.com/OSU-NLP-Group/SkillWeaver && cd SkillWeaver
  pip install -r requirements.txt      # 按 README 为准
  # 装浏览器内核（若用 playwright）
  playwright install
  export OPENAI_API_KEY=sk-xxx          # 或其他 provider 的 key
  ```

- 最小流程：**先探索、后合成、再复用**——给一个目标网站，跑探索脚本让 agent 自主练习，再跑合成脚本把稳定操作蒸馏成 API 式 skill，落进 skill 库供后续任务调用：

  ```bash
  # 1) 探索：agent 在目标站自主点/试，产出轨迹
  python explore.py --site <url>        # 脚本名以 README 为准
  # 2) 合成：把轨迹蒸馏成 API 式 skill（search_product(x) 之类）
  python synthesize.py --from <traces>
  # 3) 复用：后续任务直接调已合成的 skill（强 agent 合成给弱 agent 用可 +54.3%）
  ```

- 无常驻服务：SkillWeaver 是**研究级脚本**，探索/合成阶段离线跑，产物是可迁移的 skill 文件，非产品化 server。

**集成方式**

| 路径 | 怎么用 | 说明 |
|------|--------|------|
| **探索脚本** | `explore.py --site <url>` | 让 agent 在新网站自主练习，产出操作轨迹 |
| **合成脚本** | `synthesize.py --from <traces>` | 把轨迹蒸馏成 API 式 skill，存入 skill 库 |
| **跨 agent 复用** | 把合成的 skill 给别的 agent 调 | 强 agent 探路、弱 agent 复用（+54.3%）；skill 是可迁移产物 |
| **任意 provider** | 配 `*_API_KEY` | 探索/合成用的 LLM 可自由切换 |
