## 一、30 秒看懂这个项目

你有没有发现，每次和 AI 助手聊天，它都不记得上次说过什么？你跟它说了十遍"我喜欢简洁的代码风格"，第十一次它还是给你写一堆冗余注释。这是因为大多数 AI 对话是"无状态"的——每次对话开始，它的记忆就被清零。

**TencentDB-Agent-Memory 就是给 AI 装上一个"长期记忆系统"。** 它像一个尽职的私人秘书，在你们聊天时默默记录关键信息（你的偏好、做过的事、下过的指令），下次聊天时自动把这些记忆"回忆"起来注入对话，让 AI 表现得好像"一直认识你"一样。

> 类比：普通 AI 是一个每天换新助理的公司——你得每天重复自我介绍。Agent Memory 是给公司配了一个有长期记忆的私人秘书——它知道你的习惯、历史决策、正在推进的项目，你一开口它就知道上下文。

## 二、技术原理（算法与原理篇）

> 只讲"凭什么能工作"的算法与原理，不写前后端工程胶水。

### 2.1 它在解决一个什么问题

AI Agent 的记忆问题本质上要回答三个难题：

1. **记什么？** 对话内容浩如烟海，哪些值得记，哪些该丢弃？把每句话都记下来会导致噪声淹没关键信息，只记关键词又会丢失上下文。
2. **怎么记？** 记忆之间会冲突（用户上个月喜欢 Vue，这个月改用 React 了）、会重复（同一个偏好被说了 20 遍）、会过时——如何自动去重、合并、更新？
3. **怎么想起来？** 用户说"继续上周的项目"，系统怎么从成百上千条记忆中精准找到相关的几条，而不是一股脑全塞进上下文窗口（那会超出 token 限制）？

传统方案（如 Mem0、LangMem）通常只做简单的"提取→向量检索→注入"，缺乏层次化整理和上下文压缩能力。TencentDB-Agent-Memory 的独特之处在于它模仿了人类记忆的分层结构：原始记录→结构化记忆→场景整理→人格画像，逐层提炼。

### 2.2 核心思路（一句话 + 类比）

**四层渐进提炼**：把对话内容像"读书笔记"一样逐层加工——先提取原子记忆（L1），再按场景归类成 Markdown 文件（L2），最后合成一份完整的人格画像（L3）。

> 类比：想象你是一个新上任的助理，老板每天跟你聊很多。你的笔记习惯是：
> - **L0（原始记录）**：逐字速记老板说的每句话——流水账
> - **L1（原子记忆）**：每天下班前把速记整理成一条条卡片——"老板喜欢简洁代码""3 月 5 日决定改用 React""老板要求每次 PR 必须有测试"
> - **L2（场景整理）**：每周把卡片按主题归档——"前端重构"文件夹、"代码规范"文件夹，每个文件是一个完整的主题综述
> - **L3（人格画像）**：每月写一份"老板工作偏好手册"——一页纸概括所有关键偏好、行事风格、项目全景
>
> 每次老板开始新对话，你先偷偷看一眼相关卡片和手册，这样你总能"记得"之前的事。

### 2.3 算法 / 原理详解

#### 2.3.1 四层记忆模型

这是整个系统的骨架。理解它，就理解了 80% 的设计。

```
L0  原始对话记录（不可变追加日志）
 │  ↓ LLM 提取
L1  原子结构化记忆（7 种类型，向量索引）
 │  ↓ LLM Agent 场景聚合
L2  场景知识块（Markdown 文件，按主题聚类）
 │  ↓ LLM Agent 人格合成
L3  人格画像文档（单个 Markdown 文件：用户画像 / 团队工作指南）
```

**L1 层的 7 种记忆类型**——这是系统对"记什么"的回答：

| 类型 | 记什么 | 举例 | 优先级范围 |
|------|--------|------|-----------|
| **persona** | 用户稳定属性：偏好、技能、价值观、习惯 | "用户偏好简洁代码风格" | 50–100 |
| **episodic** | 客观事件：行为、决策、计划 | "2026-03-05 决定将前端迁移到 React" | 60–100 |
| **instruction** | 用户的长期行为指令 | "所有 PR 必须包含单元测试" | -1（全局严格）或 70–100 |
| **work_fact** | 项目事实：需求、架构约束、决策、风险 | "系统需支持 10 万并发" | 默认 50 |
| **work_task** | 行动项：负责人、截止日期、状态 | "张三负责 API 重构，截止 3/15，状态 doing" | 默认 60 |
| **work_method** | 可复用方法：SOP、设计原则、反模式 | "数据库变更必须先跑 migration 脚本" | 默认 50 |
| **work_artifact** | 工作产物：文档、PR、提示词、设计稿 | "需求文档 v2.1 已评审通过" | 默认 40 |

前 3 种面向个人聊天场景（chat mode），后 4 种面向团队协作/编码场景（code mode）。每种类型对应不同的提取 prompt 模板和优先级策略。

#### 2.3.2 L1 提取算法：场景分段 + 记忆提取联合调用

传统做法分两步：先用一个 LLM 调用做场景分段（这段对话在聊什么话题），再用另一个调用提取记忆。TencentDB 的创新是**把两步合成一次 LLM 调用**——同时输出场景边界和记忆条目，节省一半的 API 开销。

具体流程：

```
输入：最近 N 条对话消息（默认 N=10）
  ↓
质量门控（shouldExtractL1）：
  过滤掉太短的、纯符号的、疑似提示注入的消息
  ↓
消息拆分：
  最后 10 条 = "新消息"（从中提取记忆）
  前面 5 条 = "背景"（只提供上下文，不从中提取）
  ↓
单次 LLM 调用：
  同时完成场景分段 + 记忆提取
  输出 JSON 数组：每个场景包含若干记忆条目
  每个条目有：type、priority、content、source_message_ids、metadata
  ↓
去重（见下节）
  ↓
双写：JSONL 追加 + 向量库 upsert
```

> **为什么要分"新消息"和"背景"？** 举个例子：你说了 5 句话在讨论数据库选型，然后又说了 5 句在讨论前端框架。如果不加区分地从 10 条消息里提取，LLM 可能会把数据库决策错误归到前端话题下。"背景"只帮助 LLM 理解上下文转折，但不会被提取成记忆，避免了跨场景污染。

#### 2.3.3 L1 去重算法：两阶段"召回+判断"

记忆去重是这个系统最精巧的部分之一。用户说"我更喜欢简洁的代码"，系统里已经记了"用户偏好简洁代码风格"——这两条是重复的，应该合并还是跳过？

**第一阶段：候选召回（不用 LLM，毫秒级）**

```
对每条新记忆：
  ├── Tier 1：向量召回 → 用 embedding 余弦相似度找最相似的已有记忆（top-K）
  ├── Tier 2：全文检索 → 用 BM25 关键词搜索找候选（向量不可用时的降级方案）
  └── Tier 3：跳过 → 两种搜索都不可用，直接存入
```

**第二阶段：批量 LLM 判断（单次调用处理所有新记忆）**

```
把所有新记忆 + 它们各自的候选池，打包成一次 LLM 调用
LLM 对每条新记忆输出决策：
  store  → 全新记忆，直接存入
  update → 更新已有记忆（用新内容覆盖旧内容）
  merge  → 与已有记忆合并（保留两者信息）
  skip   → 与已有记忆重复，跳过
```

> 类比：就像你整理笔记时发现两条很像的卡片。你先通过关键词快速翻找（第一阶段），找到可能重复的卡片后，再仔细对比语义决定是扔掉一条、合并两条、还是更新旧的那条（第二阶段）。关键优化是：所有新记忆的对比在**一次 LLM 调用**中完成，而不是每条单独调一次。

#### 2.3.4 主动回忆算法：混合检索 + RRF 融合

用户发一条新消息时，系统需要决定"注入哪些记忆到 AI 的上下文窗口"。这本质是一个检索问题。

系统提供三种检索策略，自动选择：

| 策略 | 方法 | 适用场景 |
|------|------|---------|
| 关键词 | BM25 全文检索 | 用户提到具体术语（"React 迁移"） |
| 向量 | embedding 余弦相似度 | 用户用不同措辞表达相同意思 |
| 混合 | RRF 融合（k=60） | 默认策略，两者兼取 |

**RRF（Reciprocal Rank Fusion）** 是一种经典的排名融合算法：

```
对每个候选记忆 d：
  RRF_score(d) = 1/(60 + rank_关键词(d)) + 1/(60 + rank_向量(d))
```

翻译成人话：一条记忆如果在关键词检索中排第 2、在向量检索中排第 5，那它的综合得分就是 1/62 + 1/65 ≈ 0.032。排得越靠前，得分越高。这种方法不依赖分数的绝对值（BM25 分数和余弦分数不可比），只看排名，所以能安全地融合两种不同来源的结果。

**上下文注入的巧妙设计——分段缓存优化**：

```
注入内容被拆成两段：
  prependContext（动态段）→ 每条对话变化的 L1 记忆 → 放在用户消息前缀
  appendSystemContext（稳定段）→ persona + 场景导航 + 工具指南 → 放在系统提示尾部
```

为什么要拆？因为 Anthropic/OpenAI 的 prompt caching 机制对**稳定的系统提示**部分可以复用缓存，不需要重新计算 token embedding。把不变的内容（persona、场景导航）放在固定位置，可以显著降低每次调用的 token 消耗和延迟。

#### 2.3.5 上下文卸载（Offload）：三级级联压缩

这是系统中算法最丰富的子系统，解决一个非常实际的问题：**对话太长，超出上下文窗口怎么办？**

当 AI 在一次对话中调用了很多工具（读文件、跑命令、搜索代码），上下文会迅速膨胀。系统设计了一个 L1→L1.5→L2→L3 的卸载管线来压缩：

```
L1 — 工具结果摘要化
  每个 tool_call/tool_result 对 → LLM 压缩成一条摘要
  附带一个 0-10 的"可替代性分数"（score）
  分数越高 = 越容易被替换 = 压缩时优先动它
  触发条件：待处理的工具对 ≥ 4 个

L1.5 — 任务边界检测
  判断当前工具调用是否属于同一个任务
  输出：任务完成？是延续还是新任务？是不是长任务？
  作用：把工具调用按任务切分成段落

L2 — Mermaid 流程图生成
  把一组工具调用转化为 Mermaid 流程图
  每个节点映射到具体的工具调用
  触发条件：未生成图的条目 ≥ 4 个，或距上次生成 > 300 秒
  效果：10 个工具调用的细节 → 一张流程图
```

**三级级联压缩**（根据上下文占用率触发）：

| 级别 | 触发条件 | 动作 | 效果 |
|------|---------|------|------|
| 温和卸载 | ≥ 50% 窗口 | 找出非当前任务的工具结果，替换分数最高的 40% 为摘要 | 保留当前任务完整性，只压缩"旧任务" |
| 激进压缩 | ≥ 85% 窗口 | 按 token 数删除最旧的 40% 消息 | 大幅缩减，可能丢失早期细节 |
| 紧急压缩 | ≥ 95% 窗口 | 删除消息直到 ≤ 60% 窗口，至少保留 2 条 | 暴力截断，只保留最近内容 |

> 类比：你出差一周带了个大箱子。箱子快满了（50%），你先把不穿的衣服压缩成真空袋（温和）；快爆炸了（85%），你扔掉已经穿过的旧衣服（激进）；拉链崩开了（95%），你只留内衣和明天要穿的正装（紧急）。

#### 2.3.6 管线调度算法

四层处理什么时候触发？这里有一个精巧的调度设计：

**L1 触发**：
- 对话条数 ≥ 阈值（默认从 1 开始，每次翻倍：1→2→4→…→稳态值）
- 空闲超时（默认 30 秒无新消息）
- 关闭时 flush

> **预热模式**很有意思：刚开始对话时 L1 非常灵敏（1 条消息就触发提取），随着对话积累逐渐降低频率。这模拟了"刚认识一个人时特别注意他说的话，熟悉后只在重要节点才更新印象"。

**L2 触发——单向定时器**：
- L1 完成后启动一个延迟定时器（默认 90 秒后）
- 但有约束：两次 L2 之间至少间隔 900 秒（15 分钟），至多 3600 秒（1 小时）
- 关键设计：触发时间**只能提前，不能推后**（downward-only）

```
L2 触发时间 = max(当前时间 + 延迟, 上次 L2 时间 + 最小间隔)
L2 完成后: 下次触发 = 当前时间 + 最大间隔
```

**L3 触发**：L2 完成后触发，全局互斥（同时只有一个 L3 任务在跑）。

### 2.4 关键流程（文字流程图）

```
用户发送消息
    ↓
MemoryProxy 拦截 → 主动回忆（auto-recall）
    ↓ 向量/关键词/混合检索
    ↓ 找到相关 L1 记忆
    ↓
注入上下文（动态记忆前缀 + 稳定 persona 后缀）
    ↓
转发给 LLM → LLM 生成回复
    ↓
回复返回给用户
    ↓ （异步）
消息写入 L0 原始日志
    ↓ （L1 触发条件满足时）
L1 提取器 → 场景分段 + 记忆提取 + 去重 → 写入向量库
    ↓ （L2 定时器触发时）
L2 场景提取器 → LLM Agent 整理 Markdown 场景文件
    ↓ （L2 完成后）
L3 人格生成器 → LLM Agent 更新 persona.md
```

### 2.5 和同类比，它妙在哪

| 特性 | Mem0 | LangMem | TencentDB Agent Memory |
|------|------|---------|----------------------|
| 记忆层次 | 单层（平铺记忆条目） | 双层（短期+长期） | **四层**（L0→L1→L2→L3 逐层提炼） |
| 去重策略 | 向量相似度阈值 | 无显式去重 | **两阶段**：向量/FTS 召回 + 批量 LLM 判断 |
| 检索方式 | 纯向量 | 纯向量 | **混合 RRF**（关键词+向量融合） |
| 上下文溢出处理 | 无 | 简单截断 | **三级级联压缩**（温和→激进→紧急） |
| 人格化整理 | 无 | 无 | **L3 persona 文档**（LLM Agent 定期合成） |
| 团队协作 | 不支持 | 不支持 | **三维租户隔离**（team/user/agent）+ 4 种团队记忆类型 |

最核心的差异化在于**四层渐进提炼**。Mem0 和 LangMem 都是"提取→检索"的扁平架构，缺少"整理"这一步。就像一个人只会在笔记本上乱写，但从不整理归纳。TencentDB 的方案强制系统定期"整理笔记"（L2）和"写自我认知"（L3），让记忆质量随时间提升而非退化。

### 2.6 局限与适用边界

1. **强依赖 LLM API**：L1/L2/L3 每一层都需要调用 LLM，一个用户一天聊 1000 轮可能产生大量额外 API 开销。官方推荐 Claude 4.6 Sonnet/Opus，成本不低。
2. **依赖腾讯云生态**：生产环境绑定 Tencent Cloud VectorDB + COS + MongoDB Atlas，本地开发虽可用 SQLite 降级，但生产部署有较强的云厂商锁定。
3. **评估框架未完全开源**：README 描述了 9 维度评估框架和 6 个评测数据集，但仓库中未找到对应的 Python 评估代码（`src/evaluation/` 目录），这部分可能仅在内部版本中提供。
4. **L2/L3 整理有延迟**：L2 最少 15 分钟间隔，L3 在 L2 之后才触发。短对话（< 5 分钟）可能来不及做场景整理就结束了。
5. **单人/小团队场景过度设计**：四层架构 + 7 种记忆类型 + 三维租户隔离，对于简单的个人助手场景可能过于复杂。

## 三、使用说明（手把手篇）

> 注意：这是一个 TypeScript 项目，使用 `pnpm` 作为包管理器。以下步骤假设你使用本地开发模式（SQLite + 本地文件存储）。

### 3.0 开始前准备

- 一台 Mac 或 Linux 电脑（Windows 需使用 WSL2）
- **Node.js 22+**：去 https://nodejs.org 下载 LTS 版本安装
- **pnpm**：安装 Node.js 后，终端执行 `npm install -g pnpm`
- 一个 **LLM API Key**（三选一）：
  - Anthropic Claude：去 https://console.anthropic.com 注册 → Settings → API Keys → Create Key（key 以 `sk-ant-` 开头）
  - OpenAI：去 https://platform.openai.com/api-keys 创建（key 以 `sk-` 开头）
  - 其他兼容 OpenAI 格式的服务（如本地 Ollama）
- 联网环境

> **什么是 API Key？** 可以理解为一把"数字钥匙"，让你通过代码调用 AI 服务。注册平台账号后，在设置页面创建一个，一串长长的字母数字组合，免费额度通常够体验用。

### 3.1 打开终端

- **Mac**：按 `Command + 空格` → 输入"终端" → 回车
- **Windows**：需要先安装 WSL2（见 https://learn.microsoft.com/zh-cn/windows/wsl/install），然后在 PowerShell 中执行 `wsl` 进入 Linux 环境
- **Linux**：`Ctrl + Alt + T`

### 3.9 常见报错与解决

| 报错 | 原因 | 解决方案 |
|------|------|---------|
| `pnpm: command not found` | 没装 pnpm | `npm install -g pnpm` |
| `node: command not found` | 没装 Node.js | 去 https://nodejs.org 安装 v22+ |
| `Error: ANTHROPIC_API_KEY is not set` | 没配置 API Key | 编辑 `.env` 文件，填入你的 key |
| `ECONNREFUSED 127.0.0.1:11434` | Ollama 服务没启动 | 先运行 `ollama serve` 启动 Ollama |
| `TypeError: ... is not a function` | 依赖版本不对 | 删除 `node_modules/`，重新 `pnpm install` |
| `SQLITE_ERROR: database is locked` | SQLite 并发冲突 | 关闭其他占用数据库的进程，或删除 `data/` 目录重新开始 |
