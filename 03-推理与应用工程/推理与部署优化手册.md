## 0. 全景:推理优化的两个战场与一个根本约束

LLM 推理分两个阶段,各自的瓶颈完全不同:

| 阶段 | 做什么 | 瓶颈 | 优化方向 |
|------|--------|------|----------|
| **Prefill(预填充)** | 并行处理整个 prompt,生成首 token | **算力(compute-bound)** | 分块、并行 |
| **Decode(解码)** | 逐 token 自回归生成 | **显存带宽(memory-bound)** | 批处理、KV-cache、投机解码 |

> **根本约束**:decode 阶段每生成一个 token 都要把整个模型权重 + KV-cache 从显存读一遍——它是**带宽瓶颈而非算力瓶颈**。这意味着:**GPU 算力大量闲置**,优化的核心是"把闲置算力用满"(增大 batch)和"少读点数据"(量化、压 KV-cache)。

衡量指标三件套:
- **TTFT(Time To First Token)**:首 token 延迟,由 prefill 决定;
- **TPOT/ITL(Time Per Output Token)**:每 token 延迟,由 decode 决定;
- **吞吐(throughput)**:总 token/秒,决定成本。延迟与吞吐通常此消彼长。

### 0.1 SLA 该定多少:可参照的目标值(决策起点)

> **所有优化都是为了 SLA 服务。先有目标值,才能判断"够不够、要不要继续优化"。** 业界已有可对照的参考线,但务必用 **p95/p99 而非平均值** 衡量——平均 200ms 的系统 p99 可能高达 3000ms,1% 用户体验差 15 倍。

| 指标 | 交互式参考目标 | 判据来源/原理 |
|------|----------------|---------------|
| **TTFT** | p95 < 200ms 为佳;< 500ms 体感"跟手";> 1s 用户已察觉;> 2s 开始烦躁 | 人类感知研究 + 业界常见 SLO;代码补全更严(< 100ms) |
| **TPOT** | ≤ 30ms(≈33 tok/s)即可,低于此再快也"看不见" | MLPerf 5.1 interactive 场景;33 tok/s ≈ 人类阅读速度 |
| **流式吞吐** | ≥ 10 tok/s 是阅读下限;< 50 tok/s 交互场景仍可能显"卡" | 阅读速度阈值(450 词/分 ≈ 10 tok/s) |
| **Goodput** | 例:p90 TTFT < 200ms **且** p90 TPOT < 50ms 的最大 RPS | 只统计"同时满足所有 SLO"的请求才算数 |

> **关键判据——TPOT 有"够用即止"的天花板**:用户读不过来比 token 来得快更慢,**TPOT 压到 30ms 以下基本是浪费**,这部分省下的预算应转去压 TTFT 或扩吞吐。对话/Copilot 类 **TTFT 主导体感**(用户在第一个字之前就感到等待);代码补全才需要端到端都快。

> **不要用"吞吐"单独考核在线服务,要用 Goodput(达标吞吐)**:只有同时满足 TTFT/TPOT/E2E 全部阈值的请求才计入。否则系统可以靠"故意拖慢快请求来抹平尾延迟"或"丢弃即将超时的请求"把指标刷好看(2024 年有论文指出朴素 goodput 定义可被钻空子,提出 smooth goodput)。

## 1. KV-cache 管理:PagedAttention 与前缀复用

### 1.1 KV-cache 是显存头号占用

自回归生成要缓存所有历史 token 的 K/V 向量避免重算。问题:它随 `序列长度 × 层数 × 头数` 线性膨胀,长上下文 + 高并发时**比模型权重还占显存**。

#### 显存估算公式(先算账,再判断是不是瓶颈)

> **决策第一步永远是算账**。KV-cache 显存有确定的闭式公式,不用压测就能估出"塞不塞得下":

```
KV-cache 字节数 = 2 × L × H_kv × d_head × T × B × bytes_per_elem
  2          —— K 和 V 两份
  L          —— 层数(num_hidden_layers)
  H_kv       —— KV 头数(GQA 用 num_key_value_heads,不是 query 头数!)
  d_head     —— hidden_size / num_attention_heads
  T          —— 序列长度(prompt + 已生成)
  B          —— batch / 并发请求数
  bytes_per_elem —— FP16/BF16=2,FP8/INT8=1
```

> **GQA 的关键判据:只数 KV 头,不数 query 头**。Llama-3-70B 用 GQA(64 query 头但仅 8 KV 头),每 token 仅 ~0.31MB;若是 MHA(64 KV 头)则 ~2.5MB/token——**8 倍差距**。这就是为什么 MHA 的 70B 在 32K 上下文要 ~80GB KV(单张 H100 都装不下),GQA 只要 ~10GB。

几个可直接参照的数量级(单请求,FP16):

| 模型 | 上下文 | KV-cache |
|------|--------|----------|
| Llama-3-8B | 128K | ≈ 16.8 GB |
| Llama-3-70B | 128K | ≈ 168 GB |
| Mistral-7B | 32K | ≈ 4.2 GB |
| Llama-3-70B(GQA) | 4K × batch 8 | ≈ 10 GB |

> **何时 KV-cache 是瓶颈(触发条件)**:当 `权重显存 + KV-cache(按目标并发×上下文估)` 逼近卡的显存,且**继续加并发就 OOM** 时,KV 就是限制吞吐的瓶颈——此时优先级是 PagedAttention(消碎片)→ 前缀缓存(去重算)→ KV 量化(FP8/INT8 直接砍一半)。反之若并发上不去是因为算力先满,那 KV 不是瓶颈,别在这浪费功夫。

### 1.2 PagedAttention:像操作系统管内存一样管 KV

传统做法给每个请求预分配一整块连续显存(按最大长度),导致**严重碎片化和浪费**(实际没用满)。vLLM 的 **PagedAttention**:

> **把 KV-cache 切成固定大小的"块(block/page)",像 OS 虚拟内存的分页一样按需分配、非连续存储,用一张块表(block table)映射逻辑位置到物理块。**

收益:
- **显存利用率从 ~20–40% 提到 >90%**,浪费几乎消除;
- 同显存能塞下**多得多的并发请求** → 吞吐大涨(vLLM 论文称 2–4× over 此前系统)。

### 1.3 前缀缓存(prefix caching):相同前缀只算一次

> **多个请求共享相同前缀(system prompt、few-shot 示例、长文档)时,这部分的 KV-cache 只算一次、跨请求复用。**

- 对话场景(每轮重发历史)、RAG(同一文档多次问)、批量任务(同一 system prompt)收益巨大;
- vLLM 的 Automatic Prefix Caching、SGLang 的 **RadixAttention**(用基数树自动管理可复用前缀)都是这个思路。SGLang 的 RadixAttention 把前缀复用做成自动的树形匹配。

## 2. 连续批处理(Continuous Batching):吞吐的关键

### 2.1 静态批处理的浪费

传统静态 batch:凑齐一批一起跑,**必须等最长的那条生成完**才能返回整批、收新请求。短请求被长请求拖死,GPU 大量空转。

### 2.2 连续批处理(又叫 in-flight batching)

> **以"迭代(iteration)"为粒度调度:每生成一个 token 就检查——完成的请求立刻退出释放资源,等待的新请求立刻插入。GPU 永远在满载跑。**

这是现代推理引擎(vLLM、TGI、TensorRT-LLM)吞吐碾压朴素实现的**最大单一因素**,常带来数倍吞吐提升(相对静态/动态批处理可达 10–20× token 吞吐)。

### 2.2.1 batch size 怎么定:吞吐 / 延迟 / 显存的三角权衡

> **batch 越大吞吐越高,但 TTFT 和 KV 显存压力同步上升,且大 batch 会让长 prefill 干扰 decode(p95/p99 抖动)。** 这不是单调取舍,而是受 KV-cache 显存封顶的三角约束。

可参照的起点(务必用真实序列长度复测):

| 场景 | batch / 并发起点判据 |
|------|----------------------|
| 7B–13B,单张 H100,**离线吞吐** | batch 32–64 通常能喂满 GPU;更小则算力闲置 |
| 70B+,**离线** | batch 8–16 即可(序列长时),再大受 KV 显存限制 |
| **在线**,低负载 | 切忌"一请求一 GPU"——单请求约浪费 90% 算力;适度批处理只小幅加延迟却大降单 token 成本 |
| 在线,有 SLA | 用 `max_num_seqs` / `max_num_batched_tokens` 调节,以 **Goodput** 为目标而非裸吞吐 |

> **调参方向判据**(vLLM 系):**调小** batched-token 预算 → 改善 TPOT(ITL);**调大** → 利好 TTFT 与吞吐。`max_num_seqs` 大 → 高负载下 RPS 高;`max_num_batched_tokens` 大 → 偏向 TPS 而非请求完成速度。

> **大 batch 的硬约束是 KV 显存**:batch×上下文 决定 KV 占用(见 §1.1 公式),所以"能开多大 batch"先由显存算账决定,而非拍脑袋。70B 这类模型只有在大 batch 下才有好的成本/性能比——这也是为什么高吞吐部署往往需要先用量化/PD 分离腾出显存来容纳大 batch。

### 2.3 Chunked Prefill:别让长 prompt 堵住解码

问题:一个超长 prompt 的 prefill 很耗时,会**阻塞**正在 decode 的其他请求(TPOT 飙升)。

> **Chunked Prefill:把长 prompt 的 prefill 切成小块,和其他请求的 decode 步**混合调度**,避免长 prefill 独占 GPU,平滑延迟。**

代价:需要平衡 chunk 大小——太小则 prefill 效率降,太大则仍会卡 decode。

> **chunk 大小参照**:Sarathi-Serve 实践中把长 prompt 切成 **256–512 token/块** 与 decode 交织,实测可消除"decode 停顿"(单个大 prefill 阻塞解码数秒),代价是平均 TTFT 略升、换来尾延迟大降与吞吐提升(Mistral-7B 提服务容量 2.6×、Yi-34B 3.7×)。
>
> **何时该上 chunked prefill(触发条件)**:监控发现 **decode 中的 TPOT 出现周期性尖刺(p99 远高于 p50)**,且尖刺与长 prompt 到达相关时,就是长 prefill 在抢 GPU——开 chunked prefill;若进一步是大模型 / 超长上下文,则升级到 PD 分离(§5.1)。

## 3. 量化(Quantization):用精度换显存与速度

### 3.1 为什么有效

decode 是带宽瓶颈,**权重读得越少越快**。量化把权重从 FP16(16 位)压到 INT8/INT4/FP8,直接减少显存占用和带宽消耗。

### 3.2 主流方案

| 方案 | 精度 | 特点 |
|------|------|------|
| **GPTQ** | INT4/INT3 | 训练后量化(PTQ),逐层用 Hessian 信息最小化误差,需校准集 |
| **AWQ** | INT4 | 激活感知,保护"重要权重通道"不被量化,精度更稳 |
| **FP8(E4M3)** | 8 位浮点 | 现代 GPU(Hopper+)原生支持,精度损失小、速度快,推理首选 |
| **INT8(LLM.int8)** | 8 位 | 对离群值用 FP16 混合,几乎无损但提速有限 |

#### 高精度基线:BF16 vs FP16 怎么选

> **同样 16 位,分配不同:FP16 = 5 指数位 + 10 尾数位(精度高、范围窄,最大仅 65504,易溢出);BF16 = 8 指数位 + 7 尾数位(范围等同 FP32,精度略低)。** 显存占用两者相同。

- **现代模型默认 BF16**:动态范围大、几乎不需 loss scaling,数值更稳,且训练就是 BF16,推理保持一致最省心;
- **FP16 作为退路**:Ampere 之前的老 GPU 不支持 BF16,或需要对小数值高精度的特定推理场景;
- **判据**:不确定就跟随模型训练精度(权重 config 里通常写明)。把 FP16/BF16 当作"零损失基线",量化质量都相对它衡量。

#### GGUF(llama.cpp / 本地推理)的量化档位

> GGUF 是 llama.cpp 生态的量化容器,档位命名 `Q{位数}_K_{S/M/L}`:K 表示 K-quant(超块 + 混合精度),后缀 S/M/L 表示对敏感层保留高精度的程度(_M 把注意力层 / 部分 FFN 留在更高精度)。

| 档位 | 定位 | 7B 困惑度增幅(相对 FP16) | 何时用 |
|------|------|---------------------------|--------|
| **Q8_0** | 近无损 8 位 | ≈ +0.01 ppl | 要校验质量 / 显存充足;CPU 推理也快 |
| **Q5_K_M** | 高质量甜点 | 约 +0.04 ppl(70B 内可到 +0.08) | 比 Q4 明显更好,仅大 ~20–25% 体积 |
| **Q4_K_M** | **本地默认推荐** | ≈ +0.05 ppl(7B);70B 约 +0.15–0.20 | 大多数 chat/通用场景的最佳质量/体积比 |
| **Q2/Q3** | 极限压缩 | 非线性陡增 | 仅实验;宁可"小模型跑好"也别"大模型跑烂" |

> **本地选型判据**:Q4_K_M 是通用默认;**代码 / 推理任务对 Q4 的质量损失更敏感**,优先 Q5_K_M;**与其用 13B@Q2,不如用 7B@Q6**——后者更快、留更多上下文余量,质量往往还更好。

### 3.2.1 量化精度损失阈值与"必须保高精度"的场景

> **核心决策依据是一个在 Llama-3.1 全家族 50 万+ 次评测上得出的精度损失层级**,可作为选型先验(仍需在自己任务上复测):

| 格式 | 相对 BF16 的典型损失 | 适用 | **何时禁用 / 慎用** |
|------|---------------------|------|---------------------|
| **FP8(W8A8-FP)** | 基本无损(各规模) | H100/H200/Blackwell 生产默认;质量敏感任务 | 硬件不原生支持 FP8 时 |
| **INT8(W8A8-INT)** | 调好后约 0–3%(常为噪声级) | 无 FP8 的老卡;安全基线 | — |
| **AWQ INT4(W4A16)** | 约 1–2%(小模型更差) | 显存紧、70B+、要成本效率 | **小模型 + 数学/代码/推理** |
| **GPTQ INT4** | 约 2–3%(比 AWQ 掉得多) | 生态/预量化模型多 | 小模型、推理任务 |
| **< 3 bit** | 非线性、显著 | 仅实验 | 绝大多数生产场景 |

> **判据一:模型规模是 INT4 能否用的决定性因素**。小模型上 INT4(尤其 GPTQ)掉点明显;**70B 级别 4-bit 反而稳**——研究中 70B 在 4-bit 甚至比 8-bit 高 +1.89%。**所以"敢不敢 INT4"先看模型够不够大。**

> **判据二:任务类型设定红线**。**数学、代码生成、推理密集型任务必须保高精度(FP8 或至少 INT8),不要无脑 INT4**——这类任务激活范围尖锐、对量化最敏感,质量回退最明显。普通 chat/检索类则可激进些。

> **判据三:FP8 vs INT8 的本质区别是离群值**。FP8 用指数位实现"指数间隔",动态范围远宽于 INT8 的均匀间隔,因此对激活离群值更鲁棒——这是 FP8 能"近无损"而 INT8 提速有限的根因。H100 上 FP8 比 FP16 输出 token 快约 33%、质量近乎无损(Meta Llama-3.3-70B FP8:99%+ 质量恢复、延迟 -30%、吞吐 +50%)。

> **判据四:阈值要自己定,别迷信困惑度**。先定"应用可接受的最低准确率/最高困惑度",再用代表性样本或标准 benchmark 对比量化前后。**困惑度有误导性**:+2% 困惑度 ≠ 模型差 2%,与下游任务表现是非线性关系——务必同时看任务级指标,并用 canary 部署对比 FP16 基线输出。

### 3.3 权重 vs 激活 vs KV-cache 量化

- **weight-only**(GPTQ/AWQ):只量化权重,decode 提速明显,质量损失小——最常用;
- **weight+activation**(W8A8/FP8):权重和激活都量化,需处理激活离群值(SmoothQuant 把量化难度从激活"迁移"到权重);
- **KV-cache 量化**(FP8/INT8):长上下文时单独量化 KV-cache,省显存、能塞更长/更多并发,精度损失通常可接受。

### 3.4 选型直觉

- 显存够、要质量 → **FP8**(新硬件首选);
- 显存紧、要塞大模型 → **AWQ/GPTQ INT4**(质量比 GPTQ 略稳的是 AWQ);
- 长上下文挤显存 → 叠加 **KV-cache 量化**。

> **按部署形态再细分(Llama-3.1 研究结论)**:
> - **同步 / 低并发部署**:W4A16(weight-only INT4)成本效率最佳;
> - **异步 / 连续批处理 + 高端 GPU 上的中大模型**:W8A8(FP8/INT8)表现更好(算力被 batch 填满,weight-only 的带宽收益被摊薄);
> - **安全基线配方**:INT8 权重 + BF16/FP16 激活 + INT8 KV + 高精度累加,再按评测结果选择性下探 FP8 或 INT4;
> - **方法学判据**:要 INT4 或激活量化又不想掉质量 → 用 QAT(量化感知训练);只想快速覆盖 → PTQ。业界主流落地模式是"**训练用 FP16,部署用 INT4 或 FP8**"。

## 4. 投机解码(Speculative Decoding):并行换串行

### 4.1 核心思想

decode 是串行的(一次一个 token),但 GPU 算力闲置。投机解码:

> **用一个便宜的"草稿(draft)"机制一次猜多个 token,再让昂贵的目标模型一次性并行验证,接受对的、丢弃错的。一次前向验证多 token = 加速,且输出分布与目标模型完全一致(无损)。**

关键指标:**接受长度(acceptance length)**——平均每轮被接受的草稿 token 数,越高越快。

### 4.2 主流方法

- **独立草稿模型**:用一个小模型当 draft(如 7B 给 70B 当草稿)。简单但要额外模型 + 两模型分布要接近;
- **Medusa**:在目标模型上加多个并行预测头,一次预测多个未来位置,无需独立模型;
- **EAGLE / EAGLE-3**:在特征层面做自回归草稿,接受率更高,是当前 SOTA 方向;
- **MTP(Multi-Token Prediction)**:训练时就让模型自带多 token 预测层当草稿(DeepSeek-V3、GLM-5.2 用,见《GLM-5.2技术原理》)。

### 4.3 调优原则

- 盯服务端的 **accept length**:接近草稿 token 数 → 还能上调步数;远低于 → 下调(每个被拒草稿都是浪费的验证算力);
- 投机解码**在低并发/低 batch 时收益最大**(此时算力闲置多);高并发时 batch 已填满算力,收益缩小甚至变负。

### 4.4 什么时候值得上:接受率与并发的硬阈值

> **加速比与接受率 α 近似线性**:α 越高、每轮被接受越多 → 目标模型前向次数越少。所以"值不值得"基本由 α 一个量决定。

| 接受率 α | 结论 |
|----------|------|
| **α > 0.8** | 加速 2–4×,理想区间(代码、模板化文本、结构化摘要、标准客服答复) |
| **α ≈ 0.6–0.7** | 配合 γ≥5 可得 2–3× 加速,值得开 |
| **α < 0.5** | **投机解码反而拖慢吞吐**,应关闭(创意/开放生成、高熵输出、对抗 prompt 多落此区) |

> **触发条件式决策(可直接当开关逻辑)**:`若 batch_size > 32 或 输出长度 < 50 或 任务==embedding/批处理 → 用普通解码;否则开投机解码,调 num_speculative_tokens,目标 α > 0.70`。
> - **batch > 32**:历来被视为投机解码失效线——高并发下 batch 已填满算力,还要多跑一遍 draft,得不偿失;
> - **输出 < 50 token**:启动开销吃掉收益;
> - **显存吃紧(目标模型已占 90%+ VRAM)**:加 draft 会 OOM 或挤碎 KV-cache。

#### draft 模型怎么选

> **draft 质量是决定性因素**:差的 draft 提的草稿大量被拒,纯属浪费算力。

- **同家族 / 同 tokenizer 优先**:训练数据与分词对齐 → 接受率更高;
- **大小取目标的 1/10 ~ 1/50**:更小更快但接受率可能不够。AWS Trainium 实测:Qwen3-0.6B 比 1.7B 快,但接受率低约 60%,反而抵消收益——**1.7B + 7 草稿 token** 才是平衡点;
- **优先 EAGLE/EAGLE-3**:在目标模型的特征层面做草稿头,接受率约 0.8,典型加速 2.5–2.8×,vLLM 原生支持、无需单独训练 draft 模型;P-EAGLE 并行草稿在代码任务上可达 4–5×;
- **草稿步数 γ 的取舍**:加 γ 边际递减(接受率随草稿变长而下降)。Red Hat gpt-oss-120B 实测:γ 从 2→4,接受率 45.4%→28.3%,但平均接受长度 1.91→2.13 略升——**盯"平均接受长度"而非单看接受率来定 γ**。

> **vLLM 特有注意**:投机模型当前需在无张量并行下运行(主模型仍可 TP);且 EAGLE 在 vLLM 上的实测加速常低于原论文(缺树形解码、推测路径开销等)。输出仍是无损的(贪心采样与不开投机一致)。

## 5. 并行策略:单卡放不下怎么办

| 并行方式 | 切什么 | 适用 |
|----------|--------|------|
| **张量并行(TP)** | 把每层的权重矩阵切到多卡 | 单节点内多卡,通信密集(需 NVLink) |
| **流水线并行(PP)** | 把不同层分到不同卡 | 跨节点,通信少但有气泡 |
| **专家并行(EP)** | MoE 的不同专家分到不同卡 | MoE 模型必备 |
| **数据并行(DP)** | 多副本各跑一部分请求 | 横向扩吞吐 |

实践:单机多卡优先 TP;模型超大跨机用 TP+PP;MoE 用 EP 把专家摊开。

### 5.0 怎么选:先看瓶颈,再看"装不装得下"

> **一句话心智模型(按瓶颈选)**:**受请求量限制 → DP;受显存限制 → PP;受算力/延迟限制 → TP;MoE → EP。** DP 是复制扩吞吐(不会让单请求更快),PP 是按层切解决"装不下",TP 是层内切降单请求延迟。

按"模型装不装得下"逐级决策(vLLM 官方阶梯):

| 情况 | 选择 | 判据 |
|------|------|------|
| 单卡装得下 | 单卡,不并行 | 多卡反而引入通信开销 |
| 单卡装不下、单机能装、有 NVLink | **TP**(`tp=卡数`) | TP 通信密集,必须靠 NVLink;NVLink 下可高效扩到 8 卡,PCIe 超过 4 卡收益递减 |
| 卡数不能整除模型 / 无 NVLink(如 L40S) | **PP** | PP 支持不均匀切分、通信少 |
| 单机装不下(跨节点) | **TP(节点内)+ PP(跨节点)** | `tp=每节点卡数, pp=节点数` |
| 吞吐受限、模型装得下 | **DP**(多副本) | 横向扩并发 |
| MoE,低并发 | **TP + EP** | 低延迟交互更好 |
| MoE,高并发 | **DP + EP** | 高并发吞吐更好 |

> **TP 的反向陷阱(何时别过度切)**:小模型在大卡上开高 TP 会**变慢**——TP 把矩阵切小,而 GPU 擅长算大矩阵,切太碎反而吃不满算力。所以"卡多就猛开 TP"是错的,TP 度数要和模型大小匹配。

> **EP 选错的代价(MoE 专属判据)**:对 MoE 若用 TP,会把所有专家的权重矩阵都切片分发,导致 **KV-cache 被复制、显存可能膨胀 8×**;EP 则每卡只放部分专家的完整权重、只处理路由到本卡的 token,显存与通信都更省。**MoE 必用 EP**,TP 仅作为补充(混合 ETP)。

> **跨节点的扩展铁律**:尽量留在单节点内(≤8 卡)用 TP/DP;**只有超过 8 卡或跨节点时才引入 PP**(PP 有流水线气泡,阶段不均衡会增延迟)。超大规模再叠加 PD 分离(§5.1)与 N-D 并行。

### 5.1 PD 分离(Prefill-Decode Disaggregation)

> **prefill(算力瓶颈)和 decode(带宽瓶颈)对硬件需求相反。PD 分离把它们放到不同的 GPU 池,各自独立优化批处理与并行,通过 KV-cache 传输衔接。**

DeepSeek、SGLang、vLLM 的大规模部署都在用,能显著提升整体资源利用率——但增加了 KV-cache 跨节点传输的工程复杂度。

## 6. 推理引擎选型

| 引擎 | 特点 | 适合 |
|------|------|------|
| **vLLM** | PagedAttention 起家,生态最广,模型支持最全 | 通用部署,默认首选 |
| **SGLang** | RadixAttention 前缀复用 + 结构化输出强,Agent/多轮快 | 复杂 prompt、Agent、长前缀复用 |
| **TensorRT-LLM** | NVIDIA 官方,极致优化但部署门槛高 | 追求极限性能、固定模型 |
| **TGI** | HuggingFace 出品,易集成 | HF 生态、快速起步 |
| **llama.cpp / Ollama** | CPU/边缘/本地,GGUF 量化 | 本地、个人、边缘设备 |

> 经验:服务端高吞吐选 vLLM/SGLang;前缀复用重(Agent、RAG)倾向 SGLang;追极致且能吃下复杂度选 TensorRT-LLM;本地/边缘用 llama.cpp 系。

## 7. 长上下文与结构化输出

- **长上下文成本**:prefill 的算力和 KV-cache 都随长度涨。对策:前缀缓存(复用 system/文档)、KV 量化、稀疏注意力(模型侧)、PD 分离;
- **结构化输出(JSON/工具调用)**:用**约束解码(constrained decoding)/ 语法约束**(如 outlines、SGLang 的 grammar、XGrammar)强制输出合法格式,对 Agent 工具调用至关重要——比"求模型自觉输出 JSON 再解析重试"可靠得多。

### 7.1 在线 vs 离线:优化方向截然相反(先分类再调参)

> **最重要的一个架构分流判据:你的负载是交互式还是批量?二者优先级相反,放错基础设施是经典错误。**

| 维度 | 在线 / 实时 | 离线 / 批量 |
|------|------------|-------------|
| 优化目标 | **延迟**(TTFT/ITL/TPOT/E2E)+ Goodput | **吞吐 / 每美元 token** |
| 可接受 TTFT | 亚秒级 | 数秒甚至 24 小时(批 API) |
| batch 策略 | 连续批处理必备,按 SLA 限 batch | 大 batch 喂满 GPU,简单批处理即可 |
| 量化偏向 | weight-only(低并发带宽收益大) | W8A8(大 batch 算力满) |
| 典型场景 | 聊天、Copilot、用户面前等结果 | 嵌入、打分、夜间分析、ETL、批量文档处理 |

> **成本判据**:在线端点常年 20–30% 利用率,每 token 成本比组织良好的离线批处理**贵 5–10×**。所以 OpenAI/Google 的"批量/离线 API(24h 周转)"本质是一个"超高延迟换低价"的档位。
>
> **分类标准**:**只要有人在等结果,就是在线负载**,SLA 说了算;非交互的批量工作(嵌入、夜间分析、bulk 文档处理)优先离线,既省钱又给在线端点腾资源。**别用批量吞吐调好的基础设施去跑交互产品,反之亦然。**

## 8. 常见坑汇总(速查)

| 坑 | 说明 | 对策 |
|----|------|------|
| 静态批处理 | GPU 被长请求拖空转 | 连续批处理 |
| KV-cache 连续预分配 | 碎片化、显存浪费 | PagedAttention |
| 重复算相同前缀 | 浪费 prefill 算力 | 前缀缓存 / RadixAttention |
| 长 prompt 堵 decode | 其他请求 TPOT 飙升 | Chunked Prefill |
| 盲目追求低延迟 | 吞吐崩、成本高 | 明确 SLA,延迟/吞吐做权衡 |
| 量化无脑用 INT4 | 质量掉太多 | 先 FP8/AWQ,压测质量再激进 |
| 高并发还开投机解码 | batch 已满,收益变负 | 按并发动态开关 |
| 忽视 KV-cache 量化 | 长上下文塞不下 | KV FP8/INT8 |
| 求模型"自觉"输出 JSON | 格式错、重试多 | 约束解码强制语法 |
| 不压测就上线 | 数字全凭想象 | 在真实负载分布上压测 |
| 小模型上 INT4 跑推理/代码 | 小模型 4-bit 掉点重、推理任务最敏感 | 大模型才敢 INT4;推理任务保 FP8/INT8 |
| 用平均值考核延迟 | 平均 200ms 的 p99 可能 3000ms | 看 p95/p99,用 Goodput |
| 把 TPOT 压到 30ms 以下 | 用户读不过来,纯浪费预算 | 预算转去压 TTFT / 扩吞吐 |
| 小模型大卡猛开高 TP | 矩阵切太碎,算力吃不满反变慢 | TP 度数匹配模型大小 |
| MoE 用 TP 不用 EP | KV-cache 被复制、显存可能膨胀 8× | MoE 必用 EP |
| draft 模型选太小 | 接受率太低抵消加速 | 选 1/10~1/50 且同家族,或 EAGLE-3 |
| 在线产品跑在批量基础设施上 | 延迟体验差 / 成本浪费 | 先分类在线 vs 离线再调参 |

## 9. 推荐实操流程(端到端)

1. **定 SLA**:目标 TTFT、TPOT、并发量、成本上限——这决定所有取舍。
2. **选引擎**:通用 vLLM;前缀复用重选 SGLang;极限性能 TensorRT-LLM;本地 llama.cpp。
3. **开基础优化**:连续批处理 + PagedAttention + 前缀缓存(引擎默认基本都有,确认开启)。
4. **量化**:显存够用 FP8;紧张用 AWQ/GPTQ INT4;长上下文叠加 KV-cache 量化——每步压测质量。
5. **投机解码**:低并发场景开(MTP/EAGLE),盯 accept length 调步数。
6. **扩展**:单卡放不下用 TP;超大用 TP+PP;MoE 用 EP;超大规模上 PD 分离。
7. **结构化输出**:Agent/工具调用用约束解码保格式。
8. **持续压测**:用真实 prompt 长度分布和并发曲线压测,按 SLA 调参,别信默认。

### 9.1 一页纸决策速查表

> 把上文的判据浓缩成一张"看场景查动作"表(数字均为起点,务必复测):

| 你的情况 | 该做什么 | 关键阈值/判据 |
|----------|----------|---------------|
| 不知道目标 | 先定 SLA | TTFT p95<200–500ms,TPOT≤30ms,用 Goodput |
| 模型单卡装得下 | 不并行 | — |
| 单卡装不下、单机+NVLink | TP=卡数 | NVLink 高效到 8 卡,PCIe ≤4 卡 |
| 卡数不整除 / 无 NVLink | PP | — |
| 跨节点 | TP(节点内)+PP(节点数) | — |
| 吞吐不够、模型装得下 | DP 加副本 | — |
| MoE | EP(低并发+TP,高并发+DP) | 用 TP 会复制 KV、显存×8 |
| 显存够、新卡 | FP8 | 近无损 |
| 显存紧、模型≥70B | AWQ INT4 | 小模型/推理任务禁 INT4 |
| 数学/代码/推理任务 | 保 FP8 或 INT8 | INT4 掉点最明显 |
| 长上下文挤显存 | KV-cache 量化 FP8/INT8 | 先用 §1 公式算账 |
| 低并发、结构化输出 | 开投机解码(EAGLE-3) | α>0.7;batch>32 或输出<50 则关 |
| TPOT 周期性尖刺 | Chunked Prefill | chunk 256–512 token |
| 大模型大规模 | PD 分离 | 监控 prefill 抢占 decode |
| 离线批量任务 | 大 batch + 简单批处理 | 7B 用 batch 32–64;成本比在线低 5–10× |
| Agent/工具调用 | 约束解码(XGrammar 等) | — |

## 10. 一句话总结

推理优化的精髓:**认清 decode 是带宽瓶颈、prefill 是算力瓶颈,然后用连续批处理把闲置算力填满、用 PagedAttention + 前缀缓存把 KV-cache 的浪费榨干、用量化少读数据、用投机解码把串行变并行、用 TP/PP/EP/PD 分离把大模型摊开。** 最大的杠杆是**连续批处理 + KV-cache 管理**(吞吐数倍),最大的陷阱是**不压测就拍参数**——所有数字都依赖你的硬件和负载,必须实测。
