## 核心理念

1. **4 阶段按序推进**：`framework → nodes+branches → validate → narrative+export`。未完成前置阶段时，不进入下一阶段生成——上游改动会让下游产物过期，需重新生成。
2. **AI 协作，编剧主导**：每个 AI 产出都是「草稿」，经用户确认后才进入下一阶段；用户可对任何产出要求修改或否决。
3. **从用户种子生成**：用户的输入（一句话、一个场景、或一个开头）是全部素材，AI 从中提炼并生成完整故事线框架；规模遵守 `references/domain-baseline.md` §2.1 的基准。
4. **唯一硬性检查是脚本闭环校验**：分支无死路、无困死、结局可达（error=0）。写作质量原则（真实感、对白、独白）只是指导，不是关卡。

# 执行步骤

## 1. 接收用户种子
用户可能给一句话、一个场景、或一个开头——都直接进入阶段一。种子信息不足时，给用户 2-3 个方向选项（不同类型/基调/真相走向）让用户挑选后展开。

## 2. 创建项目输出目录并落盘初始文件
```
<工作目录>/interactive-film-game-<项目名>/
├── project.json   # 事实来源，按 references/data-model.md 结构，随每阶段产出增量更新
├── 剧本.md         # 阶段四导出
└── story.ink      # 阶段四导出（必须生成）
```
- `project.json` 是贯穿全程的**磁盘文件**，不是内存对象：每阶段经用户确认的字段立即写入/合并进该文件（阶段一写 storyFramework/scalePlan（含每章场结构）/endingsDesign/variables/fatalFlaw/echoPlan，阶段二写 chapters/nodes/scenes，阶段三写 lastValidation，阶段四写场背景与节点叙事内容）。
- 用户否决或要求修改时，改完重新写入文件后再继续。
- 后续脚本调用（validate / export）都以这个文件路径为输入。骨架、拓扑、内容填充与定向修复**均由 AI 直接修改 project.json**（结构硬约束见下节与阶段二说明），由阶段三 validate.js 校验兜底。

## 3. 四阶段推进

按 4 阶段顺序推进，每阶段完成时向用户展示产出并确认后进入下一阶段：

| 阶段 | 子技能目录 | 产出 |
|------|-----------|------|
| 一、故事线框架 | `references/01-story-framework.md` | 从种子直接生成：整体时间跨度 + 序章（背景交代与教学）+ 各章时间点划分 + 故事核心 + 每章场结构 + 结局设计（对应章节映射）+ 精简变量 + 主角 fatalFlaw + 回响映射 |
| 二、场内拆节点与分支 | `references/02-scene-nodes.md` | AI 直接生成每章节点骨架与分支拓扑（含节点 id 规范、即死 BE 配额；第一章开头即死 BE 加密）+ 节点剧情 + 抉择项及影响 |
| 三、结构验证 | `references/03-structure-validate.md` | 脚本校验至闭环（error=0：无死路、无困死、结局可达）+ BE 密度/结构检测摘要供用户确认 + 定向修复 |
| 四、叙事化润色 | `references/04-narrative-polish.md` | 场背景充实 + 人物出场引介（首次出场交代身份，隐藏身份角色用神秘感引介）+ 逐节点叙事文本（narrative，对白嵌于其中，独白按需）+ 导出（剧本.md / project.json / story.ink） |


## 脚本黑盒契约（硬约束）

- `scripts/` 下所有脚本一律当作黑盒：只允许执行，禁止 read 或解释其源码，禁止在思考中推演、复算或预演其输出。脚本实现与你的工作无关。
- 脚本 stdout 中的 JSON 是唯一事实：校验报告、nodeId、targetNodeId 一律原样采信与复制，不验证、不"修正"、不凭记忆重写。
- 脚本报错时只有三个动作：把 stderr 原样展示给用户 → 原样重试 1 次 → 仍失败则停下询问用户。不存在第四个动作（尤其不是读源码排查）。

## AI 直接修改 project.json 的写入口规则（硬约束）

project.json 是唯一状态载体，由 AI 直接编辑，但**必须做精确修改、禁止整文件重建**：

- **只许精确 patch，禁止整写**：用文件编辑工具对具体字段/节点做最小化修改（等价于"只覆盖提供的字段"），严禁凭对话记忆或思考中的推演重写整份 JSON——未提及的节点与字段一概不碰。
- **id 与引用规范**：新增节点按 `c<章序号>n<章内序号>` 分配本章下一个可用序号；`targetNodeId` / `exploreReturnNodeId` 必须指向已存在节点，写前先核对。
- **软锁防护**：任何带 `conditions` 的新增/修改选项，必须确保该节点仍保留至少一个无条件选项。
- **改后必校验**：每轮结构性修改后立即跑 validate.js，凭报告修复，不凭记忆自检。
- **原子性**：一次修改聚焦一件事（骨架一批、选项一批、修复一批），改完落盘再进行下一批，防止半成品状态。

## AI 生成结构的硬约束（骨架与拓扑）

由 AI 直接生成节点骨架与分支拓扑时，以下量化结构**必须遵守**（阶段三 validate.js 会逐项检测）：

- 节点 id 规范：`c<章序号>n<章内序号>`（如 `c1n3`，序章用 `c0` 前缀）；节点数组顺序 = 叙事顺序。
- 每章 20-30 个节点（序章 10-15 个）；每章 branch 占比 ≥25%。
- 即死 BE 岔口：序章 1-2 个（教学用）、正章每章 4-8 个（占选择节点 20-30%），按间隔散布全章（不堆在章尾）；第 1 章首个 BE 必须在前 5 个节点内。
- 非终章用菱形分岔组织选择（branch → 2-3 路径专属场景 → merge 汇回主线，merge 后开场台词按玩家来路差异化）；终章：最黑暗时刻 → 变量门控（conditions 写具体变量条件）→ 每结局一条专属前置场景 → 结局扇出。
- 全部非 ending 节点有玩家选项；带条件选项的节点必须有无条件保底出口；explore 节点须有 exploreReturnNodeId。
