
# 阶段一：世界锚点与规模规划（world / scale）

定义故事核心、核心主题、类型风格、世界规则、目标时长（分钟）、结局数量，并据此确定体量方案（章数、幕数、节点数、分支数、预估工时、章节大纲）。

## 完成标准

以下字段全部填写并通过自我检查：
- `storyCore`（含"主角想要什么 + 什么在阻碍"的张力）、`theme`、`genre`、`worldRules`、`durationMinutes`、`endingCount`
- 角色表（含四维心理字段）、变量表（3-6 个）、结局设计（数量 = endingCount）
- 体量方案 `scalePlan`（仅此一套即选定方案）：每幕节点数满足分支网络最小骨架，章节大纲与故事设定贴合

## 工作步骤

1. **收集设定（用户提供，AI 不得代填）**：故事核心、核心主题、类型/风格、世界规则、目标时长、结局数量—，缺项时向用户询问补齐，不要自行虚构。用户可只给一部分（如只有一句故事核心），其余逐项问清后再进入生成。

2. **角色设计**：
    - 参考当前世界设定生成2-4个主要角色供用户采纳/修改/否决。
    - 必须有1个主角(protagonist)，其余为对立角色(antagonist)/支线角色(support)
    - 每个角色的wound/lie/want/need要与故事核产生张力
    - 角色之间的关系要能自然制造冲突
    - 如已有结局线，角色设计要能支撑结局路线的差异
    - 输出样例：{"characters":[{"name":"角色名","role":"protagonist","motivation":"核心动机","relationship":"与主线的关系","wound":"心理伤痛（过去的创伤）","lie":"内心谎言（用来保护自己的错误信念）","want":"外部欲望（想得到什么）","need":"内在需求（真正需要什么）"}]}

3. **结局设计**：
    - 根据世界设定设计指定数量差异鲜明的结局供用户采纳/修改/否决。
    - 每个结局必须代表主题的不同维度（救赎/毁灭/妥协/真相…）
    - 结局之间的达成路径要互斥——选择不同的关键节点才能到达
    - 输出样例：{"endings":[{"id":"e1","title":"结局标题","type":"good","description":"此结局中玩家经历的最终命运，1-2句","triggerCondition":"达成此结局需要做的关键选择（具体）","avoidCondition":"哪些选择会让玩家偏离此结局","keyVariable":"courage>=4"}]}
        - triggerCondition：玩家需要做什么关键选择才能走向此结局（具体行为，非抽象描述）
        - avoidCondition：哪类选择会导致偏离此结局走向其他结局
        - keyVariable：如果有变量追踪，写出关键变量名和阈值（0-10量表，阈值3-6），否则留空
        - type 只能是 good / bad / neutral / secret （secret 结局需要特别隐蔽的条件。）
   
4. **变量提取**：
    - 根据故事设定和结局条件，提取出游戏需要追踪的叙事变量
    - 变量机制约定——全部变量共用同一套小整数量表，禁止百分比。玩家每做一次相关选择，变量以整数增量（通常+1，少数+2）累积，全程关键选择次数有限，变量现实上限约为0-10，不是0-100的百分比进度条。
    - 从结局条件提取变量名（如"affection_A>=3"→变量affection_A）；每个变量名用英文下划线命名；给出type/defaultValue/description；共3-6个变量。若某结局标注了"关键变量"，必须原样提取该变量名并生成对应变量，不得另造无关新变量名。结局阈值应落在0-10整数量表内（建议3-6）。
    - 输出样例：{"variables":[{"name":"affection_A","type":"counter","defaultValue":"0","description":"主角与角色A的好感度"}]}
        - counter：整数累加，defaultValue通常为"0"，现实量程0~10（如好感度、道德值）
        - flag：0或1的开关（如是否完成了某件事、是否发现了秘密）
        - relationship：关系值，量程约-5到+5，负为敌对，正为亲密
        - item：是否持有某物品/信息

5. **自我检查**：生成完成后用一句话快速自检——世界规则是否自洽、角色是否与故事核匹配、时长与规模是否合理、故事核是否包含"欲望+阻碍"的张力、规则是否是逼迫角色做艰难选择的引擎（而非设定装饰）、角色是否有内心撕裂、主题能否通过玩家选择体现。发现问题直接修正后再交付，无需输出独立审查报告。

6. **声纹卡（可选）**：为主要角色生成声音指纹（speaking_rhythm / vocabulary / defense_mechanism / lie_tells / sample_lines），供阶段三对白创作约束风格一致性。
    - 输出模版：{"speaking_rhythm":"说话节奏（快/慢，短句/长句，直接/迂回）","vocabulary":"常用词汇类型和禁用词","defense_mechanism":"压力下的语言防御机制（如转移话题、反问、沉默）","lie_tells":"说谎时的语言特征（如过度解释、突然变得礼貌）","sample_lines":["一句展示其声音特征的示例台词","另一句"]}

7. **规模规划（scale）**：依据目标市场与目标时长直接定下唯一体量方案，不做多档对比。规模由 `durationMinutes` 推导（互动影游经验值：每分钟正片 ≈ 1-1.5 个节点，即节点数 ≈ durationMinutes × 1-1.5，按故事密度和结局数量微调），再按下表选章/幕结构：
    | 目标市场 | 典型时长 | 章数 | 每章幕数 | 节点数参考 |
    |---------|---------|------|---------|-----------|
    | 短视频平台互动短剧 | 10-20 分钟 | 1-2 | 2-3 | 15-30 |
    | 中长互动剧 / 小程序剧 | 30-60 分钟 | 3-5 | 3 | 40-80 |
    | 互动影视 / 平台定制 | 60 分钟以上 | 5-8 | 3-4 | 80-150 |
    - 每幕节点数（totalNodes ÷ (chapterCount × actCountPerChapter)）不得低于 4（入口 + branch + 2 路径的最小骨架）。
    - 体量小要通过减少 chapterCount 或 actCountPerChapter 降低总量，禁止靠压低"每幕节点数"到 4 以下来凑小体量——否则会退化为单线。
    - branchCount：预估的 branch 类型节点数，与 totalNodes 的体量相称（全片 branch 占比 ≥25%）。
    - 输出模版：{"label":"方案定位（如：小程序互动剧）","chapterCount":3,"actCountPerChapter":3,"totalNodes":40,"totalBranches":14,"branchCount":10,"estimatedHours":150,"aiRationale":"依据目标市场与时长的定档理由","chapters":[{"title":"第一章：开端","brief":"主角登场，核心矛盾浮现"}]}（chapters 数组长度必须等于 chapterCount，章节标题和 brief 贴合输入的故事设定）


## 产物

`worldAnchor` / `characters` / `variables` / `endingsDesign` / `scalePlan` 字段——**确认后立即写入项目目录的 `project.json`**（已含其他阶段字段则合并写入）。向用户展示后确认，方可进入阶段二（结构与分支）。
