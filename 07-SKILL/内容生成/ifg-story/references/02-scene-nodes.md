# 阶段二：节点及分支拆解

## 工作步骤
- 字段说明见：data-model.md
- 阶段一的产出在project.json, 据此完善project.json中属于阶段二的字段（`chapters`、`nodes`、 `scenes`）
- 任务包括：节点设计、BE设计、选项设计、结局设计

## 规则
- 节点
    - 节点数：序章5-10 个节点；正章20-40个节点
    - 全部非 ending 节点必须有玩家选项；explore 节点须有 `exploreReturnNodeId`。
    - branch 节点 → 2-3 条路径专属场景 → merge 汇回主线。 （merge 后的开场台词按玩家来路差异化）
    - 全片 branch 节点占比 ≥25%；每章 ≥1 个中段分支；改变后续路径的剧情分岔节点是稀缺资源，每章 1-3 个。
    - **节点类型学（混合使用，禁止全是对话分支）**：①剧情分岔节点（改路径）②性格测验节点（即死 BE 岔口）③状态写入节点（不改路径但写 Flag/好感度，后果延迟回响）④计时压迫节点（限时选择，超时视为一种选择，全剧 0-3 个）⑤微互动节点（点击/上滑/拖拽等非分支交互，维持参与感不打断节奏，全剧 0-3 个）⑥回响读取节点（专门"兑现"此前 Flag 的场景：某角色提起你上一章做过的事、某道具因早前选择而出现/缺席——每个核心 Flag 至少对应 1 个）。
    - **章间收束**：每章末尾回到共同事件（瓶颈）进入下一章；上一章的差异通过**变量 + 内容裁剪**（某些小节因之前的选择而出现/缺席/变化）延续，不做章间真分岔。
- 主结局
    - 一章仅最多输出1-3个主结局，更多的主结局需要平行章节（从同一个章节延续而来的章节）各自产出
    - 禁止从一个节点扇出主结局，也禁止从一个节点扇出主结局所在的分支或者章节
    - **最长结局路线。** 全剧最多一个"最难结局"，路线最长，从分叉点起可再跨越 1-3 个整章才收束，沿途积累该结局专属的 Flag/好感/凭证。TE 通常走此形态。
- BE 选项
    - 即死 BE数：选项的30% - 50%
    - 至少15%-25%的节点只有一个能正确的选项、其他选项都走向 BE
    - **BE不等于真死**：BE 的本质是"选择导致故事提前终结"——主角身死只是形式之一，暴露/败露/任务失败/关系崩塌/被驱逐等命运性恶果同样成立。
    - 好感度心碎（清零）可触发角色中途 BE——把"负积累"也变成内容。
    - BE选项文案零危险预警。禁止杀/抢/撕/翻/硬闯/独吞/怒/赌命等风险词；BE 选项与安全选项一样中性、甚至更诱人（更快的捷径、更符合直觉的解决、更有诱惑力的方案）
    - 事前线索（叮嘱/忠告/前车之鉴）可选埋、鼓励埋，但是埋点必须非常隐蔽，绝不能是直接说明，仅仅能从一个词或者一句话中推导出来。
    - BE原因因必须由选项所代表的行动在当下情境中**必然触发**。consequence 须一句话说清"死亡机制链"：这个动作 → 触发情境中已存在的危险；BE 节点 script 必须把因果链演出来（动作→危险反应）
    - BE 分支标记 `isDeadEndBE: true`
    - BE 选项**不写** variableEffects
- 普通选项
    - normal 推进节点：1-3 个真选择（同目标、不同语气/变量效果）；禁止"继续"式单选项。
    - **无后果不成选择**：每个选项至少命中一类后果——即死 BE / 变量·好感度·Flag 变化 / 台词与场景差异 / 延迟回响 / 主角信息获取；每个互动点必须回答"为什么是这里"和"选完之后怎样"。选了跟没选一样，就是装饰不是选择。
    - **每个选择点四问校验**：①玩家为什么必须选（动机）②选完状态变了吗（变化）③后续剧情承认这个选择吗（承认）④不同状态组合能自然导向不同结局吗（回路）。
    - 菱形分支各路径：写 variableEffects；分岔并回后必须留下变量/Flag 痕迹并在后续对白/选项中回响（哪怕主线不变）。
    - 路线门控：用结局 keyVariable（阈值取 0-10 量表中的 3-6）。
    - **软门控优于硬门槛**：好感/Flag 不足时关闭的是"可得内容"（隐藏剧情、支线、专属结局路线），不要卡主线进度。
    - 带条件选项的节点：必须有无条件保底出口。
- 场
    - 场的 location/time/在场人物骨架随场记录写入
    - 划场依据：地点变 / 时间流逝 / 人物进出 / 道具状态变
    - 在场记录上标记每个角色的**首次出场节点**（firstAppearance）
- 人物称谓
    - 玩家即是主角，所有称呼都基于主角的视角（仅旁白、内心独白可以称呼主角为你/他，因为这两者是站在局外的表述）


## 验证
1. 执行node scripts/validate.js <项目JSON路径> --write，报告写入 project.json 的 `lastValidation`（校验不通过也会写入，便于修复后对比）。error > 0 时进程以非零码退出。
2. **把脚本 stderr 末尾的「互动密度与结构摘要」原样展示给用户**（每章节点数/BE 数/分支占比、✓/✗ 对照基准），并确认是否接受；BE 密度或节点数不达标时，先定向补齐结构再继续。密度基准值以脚本输出的摘要为唯一对照标准（定量基准已内置于 validate.js，文档不另设数字，避免双重事实源）。
3. 有 error 时做**定向修复**（structure:targeted_fix）：只做节点级补丁——加节点 / 改节点 / 加选项 / 改选项 / 设 explore 返回 / 登记结局六类；每次修复须能对应到具体 issue；新增/修改选项若带 conditions，该节点必须保留无条件选项；单轮 ≤25 处，其余留下一轮。修复按 SKILL.md「写入口规则」以精确 patch 方式直接修改 project.json。
4. 修复后**重跑校验**，展示通过率前后对比；循环至 error 清零且密度摘要经用户确认。

- `scripts/` 下所有脚本一律当作黑盒：只允许执行，禁止 read 或解释其源码，禁止在思考中推演、复算或预演其输出。脚本实现与你的工作无关。
- 脚本 stdout 中的 JSON 是唯一事实：校验报告、nodeId、targetNodeId 一律原样采信与复制，不验证、不"修正"、不凭记忆重写。
- 脚本报错时只有三个动作：把 stderr 原样展示给用户 → 原样重试 1 次 → 仍失败则停下询问用户。不存在第四个动作（尤其不是读源码排查）。
