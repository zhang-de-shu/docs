## 核心理念

1. **4 阶段按序推进**：`framework → nodes+branches → validate → narrative+export`。未完成前置阶段时，不进入下一阶段生成——上游改动会让下游产物过期，需重新生成。
2. **AI 协作，编剧主导**：每个 AI 产出都是「草稿」，经用户确认后才进入下一阶段；用户可对任何产出要求修改或否决。
3. **从用户种子生成**：用户的输入（一句话、一个场景、或一个开头）是全部素材，AI 从中提炼并生成完整故事线框架；规模遵守 `references/domain-baseline.md` §2.1 的基准。
4. **唯一硬性检查是脚本闭环校验**：分支无死路、无困死、结局可达（error=0）。写作质量原则（真实感、对白、独白）只是指导，不是关卡。

# 执行步骤

## 1. 接收用户种子
用户可能给一句话、一个场景、或一个开头——都直接进入阶段一。种子信息不足时，给用户 2-3 个方向选项（不同类型/基调/真相走向）让用户挑选后展开。

## 2. 创建项目输出目录并落盘初始文件
```
<工作目录>/ifg-story-<项目名>/
├── project.json   # 事实来源，按 references/data-model.md 结构，随每阶段产出增量更新
├── 剧本.md         # 阶段四导出
└── story.ink      # 阶段四导出（必须生成）
```
- `project.json` 是贯穿全程的**磁盘文件**，不是内存对象：每阶段经用户确认的字段立即写入/合并进该文件（阶段一写 storyFramework/scalePlan（含每章场结构）/endingsDesign/variables/fatalFlaw/echoPlan，阶段二写 chapters/nodes/scenes，阶段三写 lastValidation，阶段四写场背景与节点叙事内容）。
- 用户否决或要求修改时，改完重新写入文件后再继续。
- 后续脚本调用（validate / export）都以这个文件路径为输入。骨架、拓扑、内容填充与定向修复**均由 AI 直接修改 project.json**（结构硬约束见下节与阶段二说明），由阶段三 validate.js 校验兜底。
- **下游衔接**：本 skill 完成后，`project.json` 交给「ifg-illustration」skill（同目录下）生成配图，最终接入 ifg-runtime 小游戏框架。阶段四完成时运行 `node /root/zds/zds_app/ifg-runtime/scripts/check_delivery.js <项目目录> --story-only`，error=0 才算剧本交付完成（检查节点 id 规范、targetNodeId 闭合、章覆盖、变量/凭证引用、结局绑定）。

## 3. 四阶段推进

按 4 阶段顺序推进，每阶段完成时向用户展示产出并确认后进入下一阶段：

| 阶段 | 子技能目录 | 产出 |
|------|-----------|------|
| 一、故事线框架 | `references/01-story-framework.md` | 从种子直接生成：整体时间跨度 + 序章（背景交代与教学）+ 各章时间点划分 + 故事核心 + 每章场结构 + 结局设计（对应章节映射）+ 精简变量 + 主角 fatalFlaw + 回响映射 |
| 二、场内拆节点与分支 | `references/02-scene-nodes.md` | AI 直接生成每章节点骨架与分支拓扑（含节点 id 规范、即死 BE 配额；第一章开头即死 BE 加密）+ 节点剧情 + 抉择项及影响 |
| 三、结构验证 | `references/03-structure-validate.md` | 脚本校验至闭环（error=0：无死路、无困死、结局可达）+ BE 密度/结构检测摘要供用户确认 + 定向修复 |
| 四、叙事化润色 | `references/04-narrative-polish.md` | 场背景充实 + 人物出场引介（首次出场交代身份，隐藏身份角色用神秘感引介）+ 逐节点叙事文本（narrative，对白嵌于其中，独白按需）+ **逐节点配图提示词**（见下方硬约束）+ 导出（剧本.md / project.json / story.ink） |

**BE 选项伪装性 + 因果闭环（硬约束，适用阶段二）**：即死 BE 两条铁律缺一不可——
- **伪装性**：选项文案不得有任何危险预警——禁止杀/抢/撕/翻/硬闯/独吞/怒/赌命等风险词；BE 选项与安全选项一样中性、甚至更诱人（更快的捷径、更彻底的解决、更符合主角性格的痛快）。
- **因果必然性**：BE 的死因必须由**选项所代表的行动**在当下情境中**必然触发**，写进 consequence 时必须能一句话说清"死亡机制链"：这个动作 → 触发情境中已存在的危险 → 恶果呼应主角 fatalFlaw。不允许"作者要你死"式的无机制死亡；BE 节点 narrative 必须把这个因果链演出来（动作→危险反应→恶果），让玩家死得心服口服。
- **线索分层（软约束）**：事前线索（叮嘱/忠告/前车之鉴）可选埋、鼓励埋——埋了是"观察力测验"，不埋时因果链也必须自洽，是"性格测验"；无论如何，**事后回看必须合理**，绝不允许随机惩罚。

**节点叙事连贯性（硬约束，适用阶段四）**：每个节点的 `narrative` 必须自带完整信息且首尾衔接——①开头 1-2 句交代时间/地点/在场人物，并**承接上一节点结尾的状态**（上一拍留的悬念/动作/情绪要在本拍开头接住），禁止读者回翻前文才能明白谁在哪在干什么；②本拍结尾收在未解决处，恰好是下一拍开头的进入状态（entryState/exitState 必填）；③人物首次出场、重要道具进入、时空转换必须在**当下节点**叙述里自然带出；④章首节点承接上章钩子与时间跳跃。


**配图提示词随剧本产出（硬约束，适用阶段四）**：写 narrative 的同一批内，为每个节点生成配图提示词并写入 project.json（供下游 ifg-illustration 直接使用，避免二次创作丢失语境）——
- **三件套**：① 场景提示词（每场一条：location + environment + time_weather + art_prompt，英文）② 角色提示词（每角色一条：外貌卡 face/head/body，英文）③ 节点提示词 `node.imagePrompt`（英文，结构：style + shotType + Scene(取本场场景描述) + Story moment(节点标题+notes/narrative 摘要≤400字符) + mood(结局按类型着色) + ref 方向标注 + 满幅构图约束 + negative）。
- **shotType 判定**：在场角色含设定卡角色 → `character`（refs=[本场场景底图, 各角色 sheetPath]，ref 标注必须写明"参考图1仅作背景构图、参考图2+仅作人物外貌"）；无角色 → `scene`；特写道具时刻 → `prop`。
- **imageTier 配置**：project.json 顶层 `imageTier`：`"lean"`（默认）或 `"full"`。lean 档：start/branch/ending 节点 + 关键 normal 节点生成节点图，其余节点在 manifest 记 `reusedFrom: "<sceneId>"` 直接复用场景底图占位（运行时要求每节点有配图记录）；full 档：全部节点生成。生成哪些节点须在交付说明里列出清单供用户确认。

## 脚本黑盒契约（硬约束）

- `scripts/` 下所有脚本一律当作黑盒：只允许执行，禁止 read 或解释其源码，禁止在思考中推演、复算或预演其输出。脚本实现与你的工作无关。
- 脚本 stdout 中的 JSON 是唯一事实：校验报告、nodeId、targetNodeId 一律原样采信与复制，不验证、不"修正"、不凭记忆重写。
- 脚本报错时只有三个动作：把 stderr 原样展示给用户 → 原样重试 1 次 → 仍失败则停下询问用户。不存在第四个动作（尤其不是读源码排查）。

## AI 直接修改 project.json 的写入口规则（硬约束）

project.json 是唯一状态载体，由 AI 直接编辑，但**必须做精确修改、禁止整文件重建**：

- **只许精确 patch，禁止整写**：用文件编辑工具对具体字段/节点做最小化修改（等价于"只覆盖提供的字段"），严禁凭对话记忆或思考中的推演重写整份 JSON——未提及的节点与字段一概不碰。
- **id 与引用规范**：新增节点按 `c<章序号>n<章内序号>` 分配本章下一个可用序号；`targetNodeId` / `exploreReturnNodeId` 必须指向已存在节点，写前先核对。
- **软锁防护**：任何带 `conditions` 的新增/修改选项，必须确保该节点仍保留至少一个无条件选项。
- **改后必校验**：每轮结构性修改后立即跑 validate.js，凭报告修复，不凭记忆自检。
- **原子性**：一次修改聚焦一件事（骨架一批、选项一批、修复一批），改完落盘再进行下一批，防止半成品状态。

## AI 生成结构的硬约束（骨架与拓扑）

由 AI 直接生成节点骨架与分支拓扑时，以下量化结构**必须遵守**（阶段三 validate.js 会逐项检测）：

- 节点 id 规范：`c<章序号>n<章内序号>`（如 `c1n3`，序章用 `c0` 前缀）；节点数组顺序 = 叙事顺序。
- 每章 20-30 个节点（序章 10-15 个）；每章 branch 占比 ≥25%。
- 即死 BE 岔口：序章 1-2 个（教学用）、正章每章 4-8 个（占选择节点 20-30%），按间隔散布全章（不堆在章尾）；第 1 章首个 BE 必须在前 5 个节点内。
- 非终章用菱形分岔组织选择（branch → 2-3 路径专属场景 → merge 汇回主线，merge 后开场台词按玩家来路差异化）；终章：最黑暗时刻 → 变量门控（conditions 写具体变量条件）→ 每结局一条专属前置场景 → 结局扇出；**平行大分支结局（默认形态）**：结局原则上**不走终章门控扇出**，而是走"大分支线"——同一章内有 2 个结局时，从该章内的分岔点长出**两条完整的大分支线（每条相当于一个小章，各自 20-30 节点、4-8 个即死 BE、有专属场景与情感时刻）**，各自收束自己的结局；也允许分支点在更早章节、平行展开到后续章（如第三章程末分叉，第四、五章分别是一条支线，各自对应一个结局）。平行路线互不回流。**变量门控扇出仅作例外**：只在章容量不足以承载两条大支线、或纯 BE 阶层时使用，且仍须每结局 ≥1 专属前置场景。**最长结局路线**：全剧最多一个"最难结局"，其路线最长——从分叉点起可再跨越 1-2 个整章才收束（即分叉后第 2 章才结局），沿途积累该结局专属的 Flag/好感/凭证，TE 通常走此形态。
- 全部非 ending 节点有玩家选项；带条件选项的节点必须有无条件保底出口；explore 节点须有 exploreReturnNodeId。
