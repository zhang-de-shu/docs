# 调研报告生成器（仓库 / 模型 / 技术）

拿到一个目标——可以是**开源仓库**（GitHub URL 或项目名）、**新模型**（如 DeepSeek-V3、Qwen3）、或**新技术/方法**（如 GRPO、Ring Attention、MCP）——研究透，产出一份**零基础小白能看懂、能照着用**的中文 Markdown 调研报告。

用户给的是模型名或技术名时，skill 自己去定位对应的仓库或论文，不要求用户先给 URL。

报告 ≠ README/论文翻译。它要同时做到两件事，缺一不可：
1. **技术原理讲"凭什么能工作"**——用大白话+类比讲清底层算法/原理，**只写算法与原理，不写前后端工程胶水**（用了什么框架、目录分层、部署架构都不写）。
2. **使用说明手把手到鼠标级**——每步写清在哪操作、点什么/输什么、成功长什么样，配截图占位符供后续补图。纯技术/方法若无独立可运行仓库，使用说明退化为"怎么读这篇论文/怎么跑参考实现"，原理篇仍是重点。

## 输入

目标三类之一：
- **仓库**：GitHub URL 或项目名（名字需先搜定位）。
- **新模型**：模型名（如 `Qwen3`、`DeepSeek-V3-Flash`）——去定位其官方仓库与技术报告。
- **新技术/方法**：技术名（如 `GRPO`、`Ring Attention`、`speculative decoding`）——去定位奠基论文与参考实现仓库。

## 工作流

### 1. 定位目标（仓库或论文）

- **仓库 URL**：直接用。
- **仓库项目名**：`<项目名> github`，选官方/最权威的；仅当多个高相似候选才问用户确认。
- **新模型**：搜 `<模型名> github` 定位官方仓库，再搜 `<模型名> technical report` / `arxiv` 定位技术报告。两者都记下——仓库给使用、报告给原理。
- **新技术/方法**：搜 `<技术名> paper arxiv` 找奠基/最高引论文，再搜 `<技术名> github` 找参考实现（未必有官方仓库，有就用，没有就只靠论文）。

记下：目标类型（仓库/模型/技术）、权威仓库 URL（若有）、核心论文（若有）、主语言、一句话定位。

### 2. 并行抓取资料（报告地基）

目标类型不同，地基主源不同：**仓库型**以 README 为主源、论文为辅；**模型型**以技术报告为原理主源、仓库 docs 为使用主源；**技术型**以奠基论文为原理主源、参考实现为使用主源。同一轮并行发起，别串行等。按优先级：

1. **README / 技术报告**——仓库型抓 `https://raw.githubusercontent.com/<owner>/<repo>/main/README.md`（404 试 `master`/无后缀）；模型型/技术型优先抓技术报告/论文。最重要的单一来源。
2. **官方文档**——README 徽章/链接指向的 docs 站或仓库 `docs/` 目录，抓 quickstart/installation/concepts。
3. **论文**——README/报告有 arXiv 链接直接抓；否则搜 `<名> paper arxiv`。抓 abstract + method 段（ar5iv.org / arxiv.org/html 比 PDF 好读）。技术型目标这就是原理地基，务必抓全。
4. **关键源码**——只读承载核心算法的 1-3 个文件（从 README 的 Architecture 段或顶层目录里找，如 `core/`、`model.py`）。胶水代码（配置/CLI/测试/前端/CI）跳过。纯技术无仓库则跳过此项。
5. **联网补充**——搜 `how it works`、`vs <竞品>`、`benchmark`，补"妙在哪""局限"。

**工具降级链**：内置 `search` 搜（Cowork 环境最稳）、`WebFetch` 抓页面；`WebSearch` 作备用（部分环境不可用，失败直接换 `search`）；需 JS 渲染或登录换内置 `browser`。一个工具失败别放弃该来源。抓够支撑"原理+使用"两块就停，别无限深挖。

### 3. 写报告

读 `references/report-template.md`，**严格按其章节顺序**填。纯技术/方法类目标若无独立可运行仓库，"使用说明"章节按"怎么读这篇论文 / 怎么跑参考实现"重写，不要硬套安装运行步骤。两块要点：

**原理篇**：假设读者聪明但无领域背景，术语首次出现就解释或换类比；类比是主力武器（"就像图书馆索引卡，不逐本翻书，先查卡片定位书架"）；有论文先一句话讲核心 idea 再展开，公式下紧跟"翻译成人话就是…"；用 `A→B→C` 箭头画流程；讲懂"凭什么工作"就够，别陷推导。项目算法含量低（纯工具）则如实说"本身无复杂算法，原理在于组合了 X 技术"，把 X 讲清。

**使用说明篇**（最花心力）：把安装/运行步骤翻译成鼠标级行动指南，每步回答四问：①在哪操作 ②点/输什么 ③成功长什么样 ④截图占位符。

**截图占位符统一格式**（严格遵守）：

```
![截图：<界面或步骤名>](待补充截图)
> 截图说明：<操作后>屏幕出现<画面>，截这一幕替换占位图，务必包含<必须元素>。
```

**小白常识补丁**（程序员默认、小白黑洞，涉及就补一句或分 Mac/Windows 讲）：
- "打开终端"：Mac=应用程序→实用工具→终端；Windows=搜 PowerShell/cmd。
- "PATH"：解释"让系统在任何地方都能找到这程序" + 给设置步骤。
- "下载代码"：GitHub 绿色 `Code`→`Download ZIP`，或 `git clone`（没 git 先装）。
- "配置 API key"：去哪注册、key 长啥样、写到哪个文件哪行。
- 尖括号占位 `<xxx>`：明确写"连尖括号一起替换成你的值"。

覆盖完整生命周期：准备清单→开终端→取代码→装依赖→配置→运行→验证→常见报错。缺一段小白就断在半路。

### 4. 输出与交付

- 报告末尾"待补充截图清单"节把全文占位符汇总成编号表。
- 存到当前工作目录，文件名 `<项目名>-调研报告.md`（项目名用英文 kebab）。
- 用 Bash `date` 取系统时间填报告头"调研日期"。
- 交付时告知：文件路径、待补截图处数、关键假设、资料偏薄的章节。
