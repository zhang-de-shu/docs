# 文档协同创作工作流

本技能提供一套结构化工作流，用于引导用户进行协作式文档创作。作为一名主动的向导，带领用户走过三个阶段：上下文收集、精炼与结构化、以及读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到写文档："write a doc"、"draft a proposal"、"create a spec"、"write up"
- 用户提到具体的文档类型："PRD"、"design doc"、"decision doc"、"RFC"
- 用户看起来正要开始一项分量较重的写作任务

**初次提议：**
向用户提议一套用于协同创作文档的结构化工作流。解释这三个阶段：

1. **上下文收集（Context Gathering）**：用户提供所有相关上下文，同时 Claude 提出澄清性问题
2. **精炼与结构化（Refinement & Structure）**：通过头脑风暴和编辑，逐节迭代构建文档
3. **读者测试（Reader Testing）**：用一个全新的、无上下文的 Claude 来测试文档，在其他人阅读之前发现盲点

说明这种方法有助于确保文档在他人阅读时（包括当他们把文档粘贴进 Claude 时）也能良好运作。询问他们是想尝试这套工作流，还是更愿意自由发挥。

如果用户拒绝，就自由发挥。如果用户接受，则进入阶段 1。

## 阶段 1：上下文收集

**目标：** 缩小用户所知与 Claude 所知之间的差距，从而为后续的智能引导打下基础。

### 初始问题

先向用户询问关于该文档的元上下文：

1. 这是什么类型的文档？（例如技术规格、决策文档、提案）
2. 主要受众是谁？
3. 当有人阅读这份文档时，你期望产生什么样的影响？
4. 是否有需要遵循的模板或特定格式？
5. 还有其他需要了解的约束或背景吗？

告知他们可以用简写作答，或以任何最方便的方式倾倒信息。

**如果用户提供了模板或提到了某种文档类型：**
- 询问他们是否有可分享的模板文档
- 如果他们提供了共享文档的链接，使用相应的集成来获取它
- 如果他们提供了文件，读取它

**如果用户提到要编辑现有的共享文档：**
- 使用相应的集成来读取其当前状态
- 检查是否存在没有替代文本（alt-text）的图片
- 如果存在没有替代文本的图片，说明当他人使用 Claude 来理解文档时，Claude 将无法看到这些图片。询问他们是否希望生成替代文本。如果需要，请他们把每张图片粘贴到对话中，以便生成描述性的替代文本。

### 信息倾倒

初始问题回答完毕后，鼓励用户倾倒他们掌握的所有上下文。请求诸如以下信息：
- 项目/问题的背景
- 相关的团队讨论或共享文档
- 为什么不采用替代方案
- 组织层面的背景（团队动态、过往事故、内部政治）
- 时间压力或约束
- 技术架构或依赖关系
- 利益相关者的顾虑

建议他们不必担心整理——先把一切都倒出来就好。提供多种提供上下文的方式：
- 意识流式地倾倒信息
- 指向可供阅读的团队频道或讨论串
- 链接到共享文档

**如果有可用的集成**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），提及可以用它们直接拉取上下文。

**如果未检测到集成，且处于 Claude.ai 或 Claude 应用中：** 建议他们可以在 Claude 设置中启用连接器（connectors），以便直接从消息应用和文档存储中拉取上下文。

告知他们在完成初次倾倒后会被问到澄清性问题。

**在上下文收集期间：**

- 如果用户提到团队频道或共享文档：
  - 若集成可用：告知他们现在会读取相应内容，然后使用相应的集成
  - 若集成不可用：说明缺乏访问权限。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到了未知的实体/项目：
  - 询问是否应搜索已连接的工具以了解更多
  - 在搜索前先等待用户确认

- 随着用户提供上下文，持续追踪已了解的内容以及仍不清楚的地方

**提出澄清性问题：**

当用户示意已完成初次倾倒（或在提供了大量上下文之后），提出澄清性问题以确保理解到位：

根据上下文中的空白，生成 5-10 个带编号的问题。

告知他们可以用简写作答（例如 "1: yes, 2: see #channel, 3: no because backwards compat"）、链接更多文档、指向要阅读的频道，或者继续倾倒信息。以对他们而言最高效的方式进行。

**退出条件：**
当所提的问题体现出理解——即能够针对边缘情况和权衡取舍进行提问，而无需再解释基础知识时，就说明已收集到足够的上下文。

**过渡：**
询问在此阶段是否还有更多上下文想要提供，或者是否可以进入文档起草环节。

如果用户想补充更多，就让他们补充。准备就绪后，进入阶段 2。

## 阶段 2：精炼与结构化

**目标：** 通过头脑风暴、筛选和迭代精炼，逐节构建文档。

**给用户的说明：**
说明文档将逐节构建。对于每一节：
1. 会就该节应包含哪些内容提出澄清性问题
2. 头脑风暴出 5-20 个选项
3. 用户指明保留/删除/合并哪些
4. 起草该节
5. 通过精准的编辑对其进行精炼

从未知最多的那一节开始（通常是核心决策/提案），然后依次处理其余部分。

**章节顺序：**

如果文档结构已经明确：
询问他们想从哪一节开始。

建议从未知最多的那一节入手。对于决策文档，通常是核心提案；对于规格文档，通常是技术方案。总结性章节最好留到最后。

如果用户不知道自己需要哪些章节：
根据文档类型和模板，为该类文档建议 3-5 个合适的章节。

询问这个结构是否合适，或者他们是否想做调整。

**一旦结构达成一致：**

创建文档的初始结构，所有章节使用占位文本。

**如果可以访问 artifacts：**
使用 `create_file` 创建一个 artifact。这为 Claude 和用户都提供了一个可供参照的骨架。

告知他们将创建带有所有章节占位符的初始结构。

创建 artifact，包含所有章节标题以及简短的占位文本，如 "[To be written]" 或 "[Content here]"。

提供骨架链接，并说明现在可以开始填写每个章节了。

**如果无法访问 artifacts：**
在工作目录中创建一个 markdown 文件。为其取一个合适的名字（例如 `decision-doc.md`、`technical-spec.md`）。

告知他们将创建带有所有章节占位符的初始结构。

创建文件，包含所有章节标题和占位文本。

确认文件名已创建，并说明现在可以开始填写每个章节了。

**对于每一节：**

### 步骤 1：澄清性问题

宣布将开始处理 [SECTION NAME] 章节。就应包含哪些内容提出 5-10 个澄清性问题：

根据上下文和该节的目的，生成 5-10 个具体问题。

告知他们可以用简写作答，或者只需指明有哪些要点需要覆盖。

### 步骤 2：头脑风暴

针对 [SECTION NAME] 章节，视其复杂程度头脑风暴出 [5-20] 项可能包含的内容。留意：
- 之前分享过但可能被遗忘的上下文
- 尚未提及的角度或考量

根据该节的复杂程度，生成 5-20 个带编号的选项。结束时，提议如果他们想要更多选项，可以继续头脑风暴。

### 步骤 3：筛选

询问哪些要点应当保留、删除或合并。请求简短的理由说明，以帮助了解他们在后续章节中的优先级偏好。

提供示例：
- "Keep 1,4,7,9"
- "Remove 3 (duplicates 1)"
- "Remove 6 (audience already knows this)"
- "Combine 11 and 12"

**如果用户给出自由形式的反馈**（例如 "looks good" 或 "I like most of it but..."）而非带编号的选择，则从中提取他们的偏好并继续推进。解析他们想要保留/删除/更改的内容并应用。

### 步骤 4：查漏

根据他们所选的内容，询问 [SECTION NAME] 章节是否还遗漏了什么重要内容。

### 步骤 5：起草

使用 `str_replace` 将此节的占位文本替换为实际起草的内容。

宣布现在将根据他们所选的内容起草 [SECTION NAME] 章节。

**如果使用 artifacts：**
起草后，提供 artifact 的链接。

请他们通读一遍并指出需要更改之处。指出说得越具体，越有助于为后续章节积累经验。

**如果使用文件（无 artifacts）：**
起草后，确认完成。

告知他们 [SECTION NAME] 章节已在 [filename] 中起草完成。请他们通读一遍并指出需要更改之处。指出说得越具体，越有助于为后续章节积累经验。

**给用户的关键说明（在起草第一节时包含）：**
提供一条提示：不要直接编辑文档，而是请他们指出需要更改的内容。这有助于为后续章节了解他们的风格。例如："Remove the X bullet - already covered by Y" 或 "Make the third paragraph more concise"。

### 步骤 6：迭代精炼

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（切勿重新打印整份文档）
- **如果使用 artifacts：** 每次编辑后提供 artifact 链接
- **如果使用文件：** 只需确认编辑已完成
- 如果用户直接编辑了文档并要求你读取它：在心里记下他们所做的更改，并在后续章节中加以留意（这体现了他们的偏好）

**持续迭代**，直到用户对该节满意。

### 质量检查

在连续 3 次迭代都没有实质性改动之后，询问是否有内容可以删除而不损失重要信息。

当一节完成后，确认 [SECTION NAME] 已完成。询问是否准备好进入下一节。

**对所有章节重复此过程。**

### 接近完成

在接近完成时（80% 以上的章节已完成），宣布打算重新通读整份文档，并检查：
- 各章节之间的流畅性与一致性
- 冗余或矛盾之处
- 任何感觉像"注水"或泛泛套话的内容
- 是否每一句话都有分量

阅读整份文档并给出反馈。

**当所有章节都已起草并精炼完毕：**
宣布所有章节均已起草完成。表明打算再次审阅完整的文档。

审阅整体的连贯性、流畅性和完整性。

给出任何最终建议。

询问是否准备好进入读者测试，或者他们是否还想再精炼些什么。

## 阶段 3：读者测试

**目标：** 用一个全新的 Claude（无上下文渗漏）测试文档，验证它对读者是否有效。

**给用户的说明：**
说明现在将进行测试，看看这份文档对读者是否真正有效。这能发现盲点——那些对作者而言合情合理、却可能让他人困惑的地方。

### 测试方法

**如果可以访问子代理（sub-agents，例如在 Claude Code 中）：**

直接进行测试，无需用户参与。

### 步骤 1：预测读者问题

宣布打算预测读者在试图查找这份文档时可能提出的问题。

生成 5-10 个读者现实中会提出的问题。

### 步骤 2：用子代理测试

宣布这些问题将由一个全新的 Claude 实例（不含本次对话的任何上下文）来测试。

对于每个问题，只带上文档内容和该问题来调用一个子代理。

针对每个问题，总结"读者 Claude"答对/答错了什么。

### 步骤 3：运行额外检查

宣布将进行额外检查。

调用子代理，检查歧义、错误假设和矛盾之处。

总结发现的任何问题。

### 步骤 4：报告并修复

如果发现问题：
报告"读者 Claude"在某些具体问题上遇到了困难。

列出这些具体问题。

表明打算修复这些空白。

回到对有问题章节的精炼环节。

---

**如果无法访问子代理（例如 claude.ai 网页界面）：**

需要由用户手动进行测试。

### 步骤 1：预测读者问题

询问人们在试图查找这份文档时可能提出哪些问题。他们会在 Claude.ai 中输入些什么？

生成 5-10 个读者现实中会提出的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开一个全新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用已启用连接器的共享文档平台，则提供链接）
3. 向"读者 Claude"提出生成的那些问题

对于每个问题，指示"读者 Claude"提供：
- 答案
- 是否有任何含糊或不清楚之处
- 文档假定读者已经知道哪些知识/上下文

检查"读者 Claude"是否给出正确答案，或是否有任何误解。

### 步骤 3：额外检查

同时向"读者 Claude"询问：
- "What in this doc might be ambiguous or unclear to readers?"（这份文档中有哪些内容对读者可能含糊或不清楚？）
- "What knowledge or context does this doc assume readers already have?"（这份文档假定读者已经具备哪些知识或上下文？）
- "Are there any internal contradictions or inconsistencies?"（是否存在任何内部矛盾或不一致？）

### 步骤 4：根据结果迭代

询问"读者 Claude"答错了什么或在哪里遇到了困难。表明打算修复这些空白。

回到对任何有问题章节的精炼环节。

---

### 退出条件（两种方法通用）

当"读者 Claude"能够持续正确地回答问题，并且不再暴露出新的空白或歧义时，文档就准备就绪了。

## 最终审阅

当读者测试通过后：
宣布文档已通过"读者 Claude"测试。在完成之前：

1. 建议他们自己再做一次最终通读——他们是这份文档的主人，对其质量负责
2. 建议再核对一遍任何事实、链接或技术细节
3. 请他们确认文档是否达到了他们想要的影响

询问他们是否想再审阅一次，还是工作已经完成。

**如果用户想要最终审阅，就提供。否则：**
宣布文档完成。提供几条最终建议：
- 考虑在附录中链接本次对话，以便读者了解文档是如何形成的
- 用附录来提供深度，而不至于让正文臃肿
- 随着从真实读者那里收到反馈，及时更新文档

## 高效引导的技巧

**语气：**
- 直接、有条理
- 当理由会影响用户行为时，简要说明理由
- 不要试图"推销"这套方法——只管执行它

**处理偏离：**
- 如果用户想跳过某个阶段：询问他们是否想跳过并自由写作
- 如果用户显得沮丧：承认这比预期花了更长时间。建议一些加快进度的方式
- 始终给予用户调整流程的主动权

**上下文管理：**
- 全程中，如果对提到的某件事缺少上下文，主动询问
- 不要让空白累积——它们一出现就及时处理

**Artifact 管理：**
- 使用 `create_file` 起草完整的章节
- 所有编辑都使用 `str_replace`
- 每次更改后都提供 artifact 链接
- 切勿把 artifacts 用于头脑风暴列表——那只是对话而已

**质量优于速度：**
- 不要匆匆走完各个阶段
- 每次迭代都应带来有意义的改进
- 目标是产出一份对读者真正有效的文档
