## 一、产品概述

### 1.1 产品定位

「了解世界」是一个**极简入口、极深能力**的问答应用：

- **极简入口**：整个产品只有一个对话框。没有信息流、没有功能菜单、没有学习成本。用户把「想知道的任何事」——一段文字、一张照片、一个链接——丢进去，就能得到答案。
- **极深能力**：对话框背后是一个智能体（Agent）系统，它能看图、能联网查、能翻自己的知识库，并且会**核实**后再回答。

### 1.2 愿景与价值主张

市面上大多数 AI 问答的痛点是「一本正经地胡说八道」（幻觉）。「了解世界」的核心差异化承诺是：

> **真实**：答案基于可溯源的事实（搜索结果、权威数据源、自建数据库），而非模型的自由发挥。
> **准确**：多源交叉验证 + 事实核查后才输出；不确定的就明说不确定，并给出置信度。
> **坦诚**：每条关键结论都附来源；查不到就说查不到，绝不编造。

一句话 slogan：**「问世界，世界如实回答。」**

### 1.3 目标用户

| 用户群 | 典型诉求 |
|---|---|
| 学生 / 求知者 | 查概念、查事实、查数据，要求可靠可引用 |
| 职场人士 | 快速核实行业动态、政策文件、公司/产品信息 |
| 生活场景用户 | 拍个东西问「这是什么」「这个标志什么意思」「这药怎么吃」 |
| 研究/写作者 | 需要带出处的事实依据，而非泛泛而谈 |

## 二、用户场景与问题分类

系统需要处理的问题可分为六类，不同类型走不同的处理管线（详见第四章）：

| 类型 | 例子 | 主要依赖能力 |
|---|---|---|
| **事实查询** | "珠穆朗玛峰最新测量高度是多少？" | 联网搜索 + 指定权威源 |
| **图像理解** | 拍一朵花问"这是什么植物？有毒吗？" | 视觉模型 + 搜索核实 |
| **时效资讯** | "今天 A 股为什么大跌？" | 实时搜索（新闻源） |
| **知识解释** | "什么是量化宽松？" | 自建数据库 + 模型知识 |
| **数据查询** | "中国 2025 年 GDP 是多少？" | 自建结构化数据库 / 指定统计源 |
| **观点/对比** | "电动车和油车哪个更省钱？" | 多源检索 + 结构化对比 + 标注立场来源 |

**关键设计原则**：先对问题做意图分类，再决定调用哪些能力、调用多深。简单问题秒回，复杂问题允许"思考 10 秒查 8 个来源"。

## 三、产品形态与交互设计

### 3.1 页面结构

整个 App 只有一个页面：

```
┌─────────────────────────────────────┐
│  了解世界                     ⚙️ 👤 │  ← 顶栏：Logo、设置、历史
│                                     │
│   ┌───────────────────────────┐     │
│   │ 💬 回答内容（流式输出）      │     │
│   │ 正文……                    │     │
│   │ 📎 来源卡片：[1][2][3]     │     │
│   │ ✅ 置信度：高 ｜ 核实于3个来源│    │
│   └───────────────────────────┘     │
│                                     │
│  ┌─────────────────────────────┐    │
│  │ 📷 输入框：问世界任何事…      │    │  ← 唯一的输入入口
│  │           [📷图片] [🎤] [➤]  │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
```

### 3.2 输入方式

- **文字输入**：主输入方式。
- **图片输入**：拍照 / 相册选图，支持一次最多 4 张。配合文字提问，也可只发图（系统自动推断"这是什么"）。
- **语音输入**：语音转文字后走同一管线（可放二期）。
- **链接输入**：粘贴 URL，系统自动抓取网页内容理解后回答。

### 3.3 输出规范（这是"真实准确"的产品化呈现）

每条回答必须包含三部分：

1. **结论区**：直接给出答案，流式输出。
2. **来源区**：每条关键事实带角标 `[1][2]`，底部来源卡片展示：来源名称、标题、发布时间、链接。**指定权威数据源**的回答带特殊标识（如 🏛️ 官方数据）。
3. **置信度标识**：
   - ✅ **高**：≥2 个独立可靠来源一致，或来自权威数据源
   - ⚠️ **中**：仅单一来源，或来源间有出入（同时展示分歧）
   - ❓ **低/未知**：查无实据，明确回答"目前未找到可靠信息"

4. **过程可视化**（可折叠）：展示"正在搜索…→ 查阅了 XX 数据库 → 交叉核对 3 个来源"的实时步骤，让"认真查证"被用户看见，建立信任。

### 3.4 会话管理

- 历史会话列表（侧滑或顶栏进入）。
- 支持追问、多轮上下文（上下文窗口内自动携带历史）。
- 支持对回答点「👍准确 / 👎有误」，差评回答自动进入人工复核队列，同时反馈给检索与提示词优化。

```

│                       客户端层                              │
│   App（iOS/Android）或 小程序/Web：单一对话框 + 流式渲染      │

                           │
┌──────────────────────────┴─────────────────────────────────┐
│                  编排层 Agent Orchestrator（核心）           │
│                                                              │
│  ① 意图理解与分类  ② 查询规划（要不要搜/查库/看图、搜什么）    │
│  ③ 并行调度各能力   ④ 证据融合与冲突检测                      │
│  ⑤ 事实核查        ⑥ 置信度评估  ⑦ 回答生成与引用标注         │

│  多模态模型     │ │   检索能力层      │ │   自建知识库层      │
│  （大脑）       │ │  （联网搜索）      │ │  （自建数据库）     │
│ 文本理解/生成   │ │ 通用搜索 API      │ │ 向量库（非结构化）  │
```

### 4.2 一次提问的完整流程

以用户发一张植物照片 + 问"这是什么？有毒吗？"为例：

```
1. [输入] 图片 + 文字进入编排层
2. [意图分类] → "图像识别 + 事实查询" 复合意图
3. [图像理解] 多模态模型看图：
   "疑似夹竹桃科植物，叶片对生、革质，花白色五瓣……"
4. [查询规划] 生成检索词："夹竹桃 毒性"、"夹竹桃科 常见观赏植物"
5. [并行检索]
   ├─ 通用搜索 → 获得 6 条网页证据
   ├─ 指定权威源（植物志/中科院植物研究所数据库）→ 命中"夹竹桃"
   └─ 自建数据库 → 命中《常见有毒植物》条目
6. [证据融合] 三个来源一致确认：夹竹桃（Nerium oleander），全株有毒
7. [置信度评估] 多源一致 + 权威源命中 → 高置信度
8. [回答生成] 结论 + 毒性说明 + 安全提醒 + 来源角标 [1][2][3]
9. [输出] 流式返回客户端
```

### 4.3 编排层设计要点

编排层是系统的"总指挥"，建议以 **Agent 工作流**实现（而非单次大模型调用）：

- **意图路由器（Router）**：轻量模型/规则做第一级分类——纯闲聊、事实查询、图像问题、数据查询、深度研究，分别进入不同管线，控制成本与延迟。
- **查询规划器（Planner）**：把用户问题拆解为 1~N 个子查询，决定每个子查询走搜索还是走自建库。
- **并行执行器**：搜索、查库、看图并行发起，整体延迟取决于最慢一路，设 8~15 秒超时兜底。
- **证据融合器（Fusion）**：对所有证据做去重、聚类、冲突检测（见第八章）。
- **核查器（Verifier）**：对草稿回答中的每条事实断言反查证据，无证据的句子必须删掉或改写为"待核实"。

## 五、核心能力一：图像理解

### 5.1 能力范围

| 场景 | 说明 |
|---|---|
| 识别类 | 动植物、商品、地标、文字（OCR）、图表、证件/单据 |
| 解读类 | "这个标志什么意思""这张化验单正常吗""这道题怎么做" |
| 描述+检索联动 | 先描述图像特征，再生成检索词联网核实（识别不靠模型瞎猜，靠"看图→查证"闭环） |

### 5.2 模型选型建议

| 方案 | 推荐模型 | 特点 |
|---|---|---|
| **国内云 API（推荐首选）** | 通义千问 Qwen-VL-Max / 豆包视觉模型 / GLM-4V / 智谱 CogVLM | 中文场景强、合规、按量付费、接入快 |
| 国际云 API | GPT-4o / Claude（视觉）/ Gemini | 综合能力强，但需考虑合规与网络 |
| 自部署（成本敏感/隐私敏感时） | Qwen2.5-VL-72B 或 7B | 单卡可跑 7B，72B 效果接近闭源旗舰 |

**策略**：识别类问题用视觉模型输出"候选 + 特征描述"，**永远**把候选交给检索层验证后再定论。视觉模型单独识别的准确率不足以支撑"真实准确"的承诺。

### 5.3 图像处理链路

```
原图 → 安全审核（涉政涉黄拦截）→ 压缩/旋转校正
     → 视觉模型（识别+描述）
     → OCR（若含文字，并行执行）
     → 生成验证检索词 → 检索层核实 → 融合回答
```

## 六、核心能力二：联网搜索与指定数据源

### 6.1 双层搜索体系

**第一层：通用搜索（广度）**

| 选项 | 说明 |
|---|---|
| 博查 AI 搜索 API / 博查 | 国内面向 AI 的搜索 API，返回结构化摘要，推荐 |
| Bing Web Search API | 覆盖面广，中文支持好 |
| Serper / SerpAPI（Google） | 质量高，但国内访问与合规需评估 |
| Tavily | 专为 LLM 设计的搜索 API，自带正文抽取 |

建议主用一家 + 备一家做容灾，避免单点故障。

**第二层：指定权威数据源（深度与可信度）**

这是「了解世界」区别于普通 AI 搜索的关键。针对高价值领域，**定向对接权威站点**，其结果在证据融合时权重最高：

| 领域 | 指定数据源示例 |
|---|---|
| 政府/政策 | 中国政府网、各部委官网（gov.cn 域名白名单） |
| 统计数据 | 国家统计局、央行、世界银行、IMF |
| 科学/学术 | 中科院官网、知网/万方（需授权）、PubMed、arXiv |
| 医疗健康 | 国家卫健委、国家药监局、默沙东诊疗手册、UpToDate（需授权） |
| 法律法规 | 国家法律法规数据库（flk.npc.gov.cn）、裁判文书网 |
| 财经行情 | 交易所官网、持牌行情数据商（如东方财富/同花顺 API） |
| 植物/物种 | 中国植物志（iPlant）、物种 2000 |
| 新闻时事 | 官方媒体白名单（新华社、央视、人民日报等） |

**实现方式（三选一或组合）：**
1. **站点限定搜索**：搜索 API 加 `site:` 语法或域名白名单过滤（最省事，先做这个）；
2. **定向爬虫 + 入库**：对可抓取的高价值站点定期抓取、解析、入自建库（质量最高，二期做）；
3. **官方 API / 数据授权**：统计局、行情商等有 API 的直接对接（最规范，按需谈）。

### 6.2 来源信誉评分（Source Credibility）

每个来源维护一个信誉分，用于证据融合时的加权：

```
信誉分 = 基础分（来源类型：政府/学术/官媒/主流媒体/百科/自媒体/论坛）
       + 历史分（该来源过往被核查证实/证伪的记录）
       - 时效惩罚（数据过旧降权，如用 2019 年数据回答 2026 年问题）
```

来源信誉库随用户反馈和人工核查持续更新——这是系统"越用越准"的机制之一。

### 6.3 网页正文处理

搜索摘要往往不够，需要：抓取原文 → 正文抽取（去广告/导航）→ 分段 → 与问题相关性打分 → 只把最相关段落送进大模型上下文。控制送入上下文的内容总量（建议单次回答 ≤ 8~12 个段落），既省 token 又降噪。

## 七、核心能力三：自建数据库

### 7.1 定位

自建数据库解决三类搜索解决不好的问题：

1. **高频问题**：常见问题秒回（命中缓存/知识库），不走搜索，又快又省；
2. **结构化精确查询**：GDP、人口、汇率、公司注册资本等数值型问题，从结构化表里取数，精确到数字，不靠模型"回忆"；
3. **领域纵深知识**：团队自建的高质量领域语料（如百科精编、行业报告、专业教材摘要）。

### 7.2 数据库构成（双库设计）

**A. 向量知识库（非结构化）**

```
语料 → 清洗 → 分块（chunk，约 500 字/块，保留重叠）
     → 嵌入模型（embedding）→ 写入向量数据库
检索：问题 embedding → 相似度 Top-K → 重排序（rerank）→ 送入上下文
```

- 向量库选型：Milvus / Qdrant / PostgreSQL+pgvector（起步推荐 pgvector，运维最简单）
- 嵌入模型：BGE-M3 / 通义 text-embedding（中文效果好）
- 重排序：BGE-reranker 或云厂商 rerank API

**B. 结构化数据库（数值/表格）**

- PostgreSQL 存储：国家/地区指标表、上市公司基础信息表、法规索引表、常见问答对（FAQ）表等。
- 查询方式：编排层把自然问题转成 SQL（Text-to-SQL），或用"模板匹配"方式取数（"XX 年 XX 国 GDP"→ 模板化查询，比自由 SQL 更稳）。
- **每条结构化数据必须带三个字段**：数值、来源、更新时间。无来源的数据不入库。

### 7.3 数据从哪来、怎么更新

| 数据类别 | 获取方式 | 更新频率 |
|---|---|---|
| 高频 FAQ | 上线后由真实问题沉淀 + 人工编写 | 每周 |
| 统计指标 | 定向抓取统计局等官网 + 人工复核入库 | 月度/随发布 |
| 领域语料 | 采购/授权 + 公开可抓取语料清洗 | 季度 |
| 热点事件档案 | 每日由系统自动聚合当日权威报道生成"事件档案"入库 | 每日 |

**数据入库红线**：任何数据入库必须记录 `来源 URL / 文献出处 + 采集时间 + 采集人（或任务ID）`；无法溯源的数据一律不入库。

### 7.4 检索优先级

回答时证据的优先级：

```
自建结构化库（带来源的精确数值）
  ≥ 指定权威源检索结果
  > 自建向量知识库
  > 通用搜索（高信誉来源）
  > 通用搜索（普通来源，仅作旁证）
```

低优先级证据与高优先级证据冲突时，以高优先级为准，并在回答中说明分歧。

## 八、真实准确的保障机制（核心设计）

这一层是「了解世界」的灵魂。共五道防线：

### 防线 1：证据先行（Grounded Generation）

- 生成回答时强制要求：**每一个事实性断言必须能映射到至少一条检索证据**。
- 提示词工程：系统提示明确"你只能基于【证据列表】回答；证据中没有的信息，不允许写入回答；宁可说'未找到可靠信息'"。
- 温度参数调低（temperature ≤ 0.3），抑制自由发挥。

### 防线 2：多源交叉验证

- 关键事实要求 ≥2 个**独立来源**（不同机构，而非同一通稿的 N 个转载）一致才可标记"高置信"。
- 转载去重：通过文本相似度 + 发布时间判断是否同源，防止"N 家媒体"其实是"一篇通稿"的假象。

### 防线 3：冲突检测与呈现

- 证据间冲突时（如两个来源数字不一致），**不私自二选一**，而是：
  - 能判断优劣（来源信誉/时效）→ 采用优者，注明"另有来源称 X"；
  - 无法判断 → 并列呈现两种说法及各自来源，交用户判断。

### 防线 4：事实核查器（Verifier）

回答草稿生成后，跑一遍自动核查：

1. 抽取草稿中所有事实断言（数字、日期、人名、结论）；
2. 逐条反查是否有证据支撑；无支撑 → 删除或降级为"有说法认为（未证实）"；
3. 数字与单位核对（万/亿、百分比、年份）——数字错误是 AI 回答最常见的翻车点；
4. 时效核对（"截至 XXXX 年"是否标注）。

### 防线 5：人工抽检与反馈闭环

- 每日随机抽检 1~2% 的回答 + 全部被点👎的回答，人工评分；
- 错误案例归因（搜索没搜到？来源不可靠？模型没用好证据？），回流优化对应环节；
- 高频错误类型沉淀为回归测试集，每次提示词/模型升级前跑一遍。

### 诚实兜底

当证据不足时，系统的标准行为是说清三件事：**查了什么来源、为什么没查到、建议用户去哪里查**。"不知道"也是一种高质量的回答。

## 九、回答生成与引用规范

### 9.1 回答模板

```
【结论】 直接回答（1~3 句）
【展开】 关键事实 + 角标引用 [1][2]
【分歧/时效】（如有）不同说法 / 数据截止时间
【来源】
 [1] 🏛️ 国家统计局《2025年国民经济和社会发展统计公报》 2026-02-28 ↗
 [2] 新华社《……》 2026-03-01 ↗
【置信度】 ✅ 高（2 个独立来源一致，含官方数据）
```

### 9.2 角标规则

- 每个事实句末尾必须带角标；无角标的事实句在核查阶段会被拦截。
- 同一来源多处引用复用同一角标。
- 来源卡片可点击跳转原文。

## 十、技术选型清单

### 10.1 推荐配置（国内合规优先，MVP 适用）

| 模块 | 推荐选型 | 备选 |
|---|---|---|
| 主模型（推理/生成） | 通义千问 Qwen-Max / DeepSeek-V3 | 豆包、GLM-4、Kimi |
| 视觉模型 | Qwen-VL-Max / 豆包视觉 | GLM-4V、自部署 Qwen2.5-VL |
| 轻量路由/意图分类 | Qwen-Turbo / DeepSeek 小杯 | 规则 + 小模型 |
| 通用搜索 API | 博查 AI 搜索 | Bing API、Tavily |
| 嵌入模型 | BGE-M3 | 通义 text-embedding |
| 重排序 | BGE-reranker-v2 | 云端 rerank API |
| 向量库 | PostgreSQL + pgvector | Milvus、Qdrant |
| 结构化库 | PostgreSQL | MySQL |
| 后端框架 | Python FastAPI（AI 生态最全） | Go（高并发网关） |
| Agent 编排 | 自研轻量工作流（状态机式）| LangGraph、Dify |
| 流式输出 | SSE（Server-Sent Events） | WebSocket |
| 客户端 | 先做微信小程序（获客最快）或 Flutter 双端 App | React Native |
| 对象存储 | 阿里云 OSS / 腾讯云 COS | MinIO（自建） |
| 部署 | 阿里云/腾讯云容器服务 | 单机 Docker（起步） |
| 监控 | 日志 + 链路追踪（Langfuse 管 LLM 调用链）| 自建 |

### 10.2 关于"编排框架自建还是用现成"

MVP 阶段建议**自研轻量工作流**（意图路由 → 规划 → 并行检索 → 融合 → 核查 → 生成，就是一个有限状态机），原因：链路清晰可控、便于做核查定制、不被框架绑架。Dify/LangGraph 可用于快速验证，但核心核查逻辑长期要掌握在自己手里。

## 十一、安全与合规

### 11.1 内容安全

- 输入输出双向过滤：接入云厂商内容安全 API（涉政/涉黄/暴恐/违禁品）；
- 医疗、法律、金融投资类问题强制附加免责提示（"不构成医疗建议/投资建议"）；
- 图像输入先过安全审核再进模型。

### 11.2 资质合规（中国大陆）

| 事项 | 说明 |
|---|---|
| 生成式 AI 服务备案 | 依据《生成式人工智能服务管理暂行办法》，面向公众上线前完成大模型备案/登记（小体量可走轻量的"登记"路径，用已备案的第三方模型 API 可大幅简化） |
| ICP 备案 / App 备案 | 网站与 App 均需备案 |
| 数据来源合规 | 爬虫遵守 robots 协议与网站条款；版权语料走授权采购；**不抓取、不存储个人隐私数据** |
| 用户隐私 | 用户上传的图片默认处理完可删除或短期留存；隐私政策明示数据用途；会话数据可一键删除 |

> 合规策略建议：MVP 期**全部使用已通过备案的第三方模型 API**（通义/豆包/DeepSeek 等均已备案），自身只做应用层，可绕开自建大模型备案的重流程。

### 11.3 防滥用

- 按用户限流（如免费 30 次/天）；
- 对"批量抓取式提问"行为识别与封禁。

## 十二、成本估算

### 12.1 单次问答成本（估算，深度问答）

| 项目 | 用量 | 成本量级 |
|---|---|---|
| 意图路由（小模型） | ~1k tokens | ≈ ¥0.001 |
| 主模型（含证据上下文，约 8k in + 1k out） | 9k tokens | ≈ ¥0.05~0.15 |
| 视觉模型（如带图） | 1 图 | ≈ ¥0.01~0.03 |
| 搜索 API | 2~5 次调用 | ≈ ¥0.02~0.10 |
| 合计 | | **约 ¥0.1~0.3 / 次深度问答** |

轻量问题（命中自建库/缓存、无需搜索）成本可低至 ¥0.01 以内——这就是自建数据库的省钱价值。

### 12.2 月度固定成本（MVP 期）

| 项目 | 估算 |
|---|---|
| 云服务器（2~4C8G × 2）+ PG + OSS | ¥800~2,000/月 |
| 内容安全 + 杂项 API | ¥200~500/月 |
| 搜索 API 包月（按 1 万次/月） | ¥500~2,000/月 |
| **合计（不含人力）** | **约 ¥1,500~4,500/月** |

按 1 万 DAU、人均 3 问/天估算，月变动成本约 ¥3~9 万——规模化后需要通过自建库命中率提升、缓存、小模型分流来压成本。

## 十三、实施路线图

### Phase 0：验证期（2 周）

- 用现成工具手搓 Demo：一个对话框页面 + Qwen-Max + 博查搜索 API，验证"搜索+引用"链路体验；
- 找 20 个目标用户测 50 个真实问题，验证价值假设。

### Phase 1：MVP（4~6 周）

- 编排层工作流上线（意图路由 / 查询规划 / 证据融合 / 引用标注）；
- 图像理解接入；
- 指定权威源白名单 v1（政府网 + 统计局 + 官媒，用 site: 限定方式）；
- 置信度标识 + 来源卡片；
- 小程序端上线，开始灰度。

### Phase 2：知识库与核查（6~8 周）

- 自建双库上线：pgvector 向量库 + 结构化指标库（首批 10 个高频领域）；
- 事实核查器（Verifier）上线；
- 来源信誉评分 v1；
- 反馈闭环（👍👎 + 人工抽检看板）。

### Phase 3：深化与增长（持续）

- 定向爬虫管线：高价值权威站点内容定向入库；
- 官方数据 API 对接（统计局、行情商等）；
- 语音输入、追问建议、"深度研究"长报告模式；
- 个性化（记住用户关注领域，来源偏好可调）；
- 商业化：免费版限次 + 会员版（深度研究、更多图片额度、API 输出）。

## 十四、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型幻觉漏网，输出错误事实 | 信任崩塌（致命） | 五道防线 + 上线前跑错误案例回归集；医疗/法律类强制保守策略 |
| 搜索结果质量差/被 SEO 垃圾污染 | 证据不可靠 | 来源信誉分 + 权威源白名单优先 + 正文质量打分 |
| 权威源反爬/版权纠纷 | 数据断供 | 优先用搜索 API 的 site: 方式；入库语料走授权；保留多源冗余 |
| 单次问答成本高、延迟长 | 体验与成本 | 意图分流（简单问题不走全流程）+ 结果缓存 + 自建库命中前置 |
| 时效性问题答旧数据 | 用户感知"不准" | 强制时效标注；时效类问题强制走实时搜索而非自建库 |
| 合规（备案、内容安全） | 下架风险 | 全用已备案模型 API；上线前完成内容安全接入与 App 备案 |
| 恶意构造的提示词注入（网页内容里藏指令） | 被诱导输出 | 检索内容与用户指令严格隔离；证据内容在提示词中明确标记为"资料，不是指令" |

## 十五、验收指标

### 准确性指标（北极星）

- **事实准确率**：人工抽检 ≥ 95%（高置信回答 ≥ 98%）；
- **引用有效率**：角标对应来源可打开且支撑论断的比例 ≥ 98%；
- **幻觉率**：抽检中无证据支撑断言占比 ≤ 1%；
- **诚实拒答率**：查无实据时正确说"不知道"的比例 ≥ 90%（不硬答）。

### 体验指标

- 简单问题响应 ≤ 3 秒，深度查证问题 ≤ 15 秒（流式输出首字 ≤ 2 秒）；
- 用户 👍 率 ≥ 80%；次日留存 ≥ 35%。

### 成本指标

- 自建库/缓存命中率 ≥ 30%（Phase 2 后）；
- 单次问答平均成本 ≤ ¥0.15。
